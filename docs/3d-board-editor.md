# Standalone 3D board editor

In the **3D Map Preview**, choose **Menu → 3D Editor** to edit the displayed map. The preview closes before the editor opens an independent copy, so edits do not change the lobby's map. File previews retain their save destination (legacy maps still import to `.board2`); generated or assembled maps open as unsaved documents.

After a successful save, closing the editor refreshes the lobby's selected-map thumbnails, available-map thumbnails and board catalogue. The normal map-settings request makes the server rescan its boards and discard any stale generated battlefield. Saving an individual source sheet already selected in the lobby preserves its placement. Saving an assembled preview or using **Save As** for a new map selects the saved map as one complete board; the assembled preview's rotation, theme and height adjustments are already saved and are not applied again. Entering the editor from the map browser closes that browser, so closing the editor returns directly to the lobby. Cancelled or failed saves do not trigger this handoff, and any later discarded edits stay out of it. Saved maps must be in a configured board directory accessible to the server; this does not upload local files to a remote server.

The launcher’s board editor actions now open a native UIKit workspace. `BoardEditorSession` owns the document, commands, selection and undo history on the EDT. `GpuMapSource` publishes immutable snapshots to the rendering thread. No `BoardView` or detached palette is created at startup, and there is no Legacy 2D editor any more (the Legacy 2D Preview below shows the document in 2D). The editor shares the existing `Board`, `Hex`, `Terrain`, artwork, camera, and picking implementations with the game. File choosers and save/discard prompts remain ordinary Swing dialogs.

Use the top-right menu’s **Legacy 2D Preview** action to open a separate, non-modal window beside the running editor that shows the edited board as the Legacy 2D board draws it. It is a `BoardView` on the session's own game and board, so it follows every edit, Undo/Redo, Open and New as they happen, with no copy and no polling. Choosing **Legacy 2D Preview** again brings the open window to the front; it stays above the editor window, and closing the editor closes it. Map preview windows switch with **View → Renderer** (Legacy 2D, Classic, Enhanced): the 3D preview's menu and the Legacy 2D window's menu bar have it, and switching keeps the exact previewed board without reloading or regenerating it. In the editor, Renderer's Legacy 2D is disabled, because the editor draws only in 3D.

Both workspaces also have **Menu → View** for the Renderer, Hex Coords and GUI scale, using the same preferences as gameplay and the Legacy 2D board. Camera, EID, and ruler controls remain in their dedicated controls and shortcuts. The editor retains Ctrl+G for Group, so its Hex Coords menu entry does not advertise that conflicting shortcut. Unit and combat overlays belong to gameplay.

The editor's Menu also has the old editor's file and help commands (parity batch C). **New** opens Settings scrolled to its Size section (New board, Random map, Resize). **Save As Image...** writes the old editor's printable PNG (`BoardArtwork.printable`: one 84 × 72 tile of 2D tileset art per hex with its labels; placed objects and decals are 3D art and do not show; the zone overlay of the old editor is gone with its painter). **Open Board Source File** opens the document's saved `.board2` in the program the system opens it with; it is disabled until the document has a file, and a failure shows in the status line. **Help** lists the keys and gestures (the tools' keys, the document keys, the mouse gestures and the camera keys as the key bindings set them now) in a native dialog; it replaces the old help labels and the old readme, `megamek/docs/Customization/Map Editor-readme.txt`, which now describes the 3D editor and keeps the board and tileset format reference. New and Help are added to the Menu by `GpuBoardEditor.menu`, because they open native dialogs; the other entries are `GpuMapSource`'s. On macOS, Quit while the editor runs asks the editor's save question, as closing its window does, and MegaMek keeps running (`GpuBoardWindow.quitHandler`; not tested on a Mac).

**Trace overlay.** Menu → View → **Trace Overlay** shows a reference image, such as a scanned paper map, over the board; **Trace Overlay Settings...** opens the Client Settings at their Overlays page, where the old Trace settings choose the image file, its opacity, scale and position. The image is a view setting (`GUIPreferences`), never part of the board, and the editor's dirty flag ignores it. It lies where the old 2D editor drew it at 100 % zoom: an image pixel at scale 100 % is a pixel of the 2D board (a hex is 84 × 72), and the position counts from the old board panel's corner, one hex left of and above the first hex, so 84, 72 puts the image's corner on hex 0101's corner and settings made for the old editor still line up. The image fits the hexes only when looking straight down, so it shows only in the top view (`GpuTraceOverlay.topView`: `BoardCamera.isTopDown` within 2° of tilt, also in the Tactical View) and fades out in 0.15 s as soon as the camera tilts away, and in again when it returns. One render pass (`GpuTraceOverlay`, in the board view's frame after the scene and before the tactical overlays) draws it over terrain, objects and units; the editor's markers, hex grid and labels stay above it. It lies on the level-0 plane: the orthographic top view shows it exactly on every hex; with the perspective lens, hexes far from level 0 and far from the view's centre shift a little against it. `GpuMapSource` copies the settings on the EDT (a trace preference change captures no board art again); only the editor has them.

## Editing

The palette includes **Space** under Ground & Water and **Wall** under Buildings.
Space keeps a selectable transparent plane and enables the shared, slowly drifting
star background. Painting adjacent walls joins their compatible building exits;
erasing a segment disconnects its neighbours. These changes save with the board
and belong to the same undo step as the stroke.

- Use as brush on any terrain layer captures the complete hex: theme, elevation, all terrain and exits, appearance, props and decals. The Brush panel identifies `Hex stamp · XXYY` and shows a 3D preview of the captured contents using the shared terrain renderer. The stamp stays unchanged when the source hex is edited or another hex is selected. Painting replaces each destination once per stroke, with fresh object and group IDs; one undo restores the whole stroke. Level and Theme start enabled and can be disabled to keep the destination's values. Erase with a hex stamp clears whole hexes. Choosing a library card leaves hex stamp mode; Use as brush on an individual object still samples only that object. Route sides are reconciled after the complete stroke, as for pasted hexes.
- The workspace: the toolbar at the top left; the camera and editor utilities at the top right, with the issues triangle to their left; the full-height Assets column on the left; the right column (Layers over Edit) on the right. The board area between them holds two corner panels, both opaque panels sized to their content: Brush at the bottom left, beside Assets, and the side view at the bottom right, beside the right column. There is no bottom strip. Hexes are written by their board number everywhere in the editor: the Edit title (`HEX 0303`), the document line, the side view and the issues. With no hex selected, Layers says so in one muted line. Each Layers row shows its type: the Ground row keeps the hexagon; water, bridge, road, woods/jungle (tree), building, heavy industry (factory) and fuel tank rows, and objects by kind and palette section: decals a paint roller, Vegetation objects a tree, rolling stock and rail terrain a train, other Transportation objects a car, animals a paw, groups a stack and any other decorative object a star; other rules terrain (rough, rubble, hazards, elevators, …) shows a generic rules icon. A component without terrain of its own, one that only adds fields (Hazards, Weather and surface conditions, Scenario features, Salvage, Elevators), has its row while any of its fields is in the hex; such a row has no remove button, because each field has its own in Edit. The font has no bridge glyph, so the bridge row uses a deck on legs. A reorderable row keeps its drag handle before its type icon. Layers are a tree (the UI kit's `UiTree`): the objects on a component's surface are nested under its row, the objects on no listed surface follow the components, and each group's row has all of the group's members in the hex nested under it. A row with nested rows has a chevron that collapses or expands it; a collapsed row stays collapsed while the same hex is inspected (also through edits, undo and new selections), and another hex starts with every row expanded. Groups are flat: an object has at most one group id, so the tree is two levels deep today.
- Assets opens on a start page: the title, one search field and a tile per palette category in two columns (Theme, Ground & water, Vegetation, Transportation, Buildings, Industry, Parks & props, Hazards & scenario, Decals), each with an icon rendered like a hex stamp from the category's sample hex in the blueprint; a mint mark shows the tile of the active brush's category. A tile opens its category page, whose header is `[<]` (back to the start page) and the category's name, a drop-down listing every category for a jump. The page lists its sections, each an upper-case caption over a hairline that starts a new row, with their cards in a two-column grid. A card arms one palette entry: a terrain card (one per terrain type; its levels are Brush rows), a look, an object or a stamp. The variants of one object are one card with a Type choice in Brush and Edit. A gallery card (`›`: Modular buildings, Single-hex buildings, Legacy building art, Legacy quay art) opens its designs in the panel, with `[<]` back to the category; a design card arms the brush, and its name takes two lines, as a gallery's designs share long names. Compositions (stamps and the 7-hex DropShip) carry a BLUEPRINT chip and stand in a Blueprints section. A decal with a purpose is in its purpose section and under Decals: one entry shown twice. The Theme page has a card per theme, Dirt and Rock (drawn by the 3D board only) under Special; a Theme card arms that theme's brush (key `theme/<id>`) and stays highlighted, with the Theme tile marked, while it is armed. Its Paint gives each hex the theme and Clear ground's look (a ground design such as Grass or Desert goes, so the new theme's clear ground shows) and keeps everything else on the hex: ground terrain (sand, mud, swamp, tundra, planted fields, ground fluff), water and lava, rough, woods, roads, buildings, the level, objects and the other owners' looks; one stroke is one undo step. Its Brush has Radius, Level (unticked) and Only overwrite clear hexes but no Theme row, since the card is its theme. A theme cannot be erased: with a Theme card Erase shows "A theme has no Erase" and changes nothing. Clear ground and the other ground cards still paint their fields, and Edit's Hex theme and Settings' Global theme are unchanged. Ground & water's Liquids section holds Water and Lava. Lava is liquid magma (`magma:2`) on the water's depth, the 3D board's lava (`HexTile.liquid`), so the Lava card is the water component's preset `water/magma` (`water:1;magma:2`) with Water's Depth row and no Current. Lava painted over water, a hazardous liquid, magma crust or dry ground makes the hex lava of the brush's depth (a hazardous liquid goes, as lava would hide it), Water painted over lava or crust makes it water (water under crust is not drawn), and Erase with either card removes liquid magma with the depth; crust stays (`BoardEditorSession.paintFields`). The search finds the Lava card by "lava" (its label) and "magma" (its key). The Hazards' Magma card (Crust or Liquid) is unchanged. The search covers every category from every page, including the designs behind gallery cards: per category, the cards whose label, member labels or keys, or section name match; clearing it returns to the page. Esc clears the search, then leaves a gallery, then a category; in the search field the first Esc clears its text and the second leaves the field. The panel reopens on the last page shown in the session. A card's tooltip is its whole name. The grid (`UiCardGrid`) shows only the visible rows of cards, plus one row on each side, and creates nothing while those rows stay the same. A card is created when it first scrolls into view and hidden when it leaves, so scrolling back a little shows its preview again without loading or rendering it anew. Cards more than 12 rows from the shown ones are removed, which releases their previews (thumbnail textures, model and terrain preview framebuffers), and are created again if they return; all cards are released when the page or the search changes. The start page's tiles are built once and only hidden while another page shows, so their icons stay rendered.
- The tools are Select (Z), Sculpt (X), Paint (C) and Erase (V), in the toolbar, the right-click menu and on the keys: map-making order (shape the ground, paint it, clean up), with Paint, the most used, under the middle finger and Erase last. Ctrl+Z, Ctrl+C and Ctrl+V keep undo, copy and paste. The toolbar shows each tool's icon and key. The bare keys switch tools only inside the editor and win over any user keybind there; a map preview keeps Z for its overview, a focused text field keeps its typing, and an open gallery, dialog or choice list ignores them. The keys are positional (GLFW), so on AZERTY the physical W key selects. There is one active brush. Choosing a paintable card activates Paint without modifying or sampling the inspected hex. The Brush panel shows only for the tools with options, with the tool and brush as its title (`Paint · Woods`) and the tool's gesture hint as its last line: Paint configures future strokes of the active brush, whatever page Assets shows, with the card's rows: Radius; Level and Theme for ground and a hex stamp (Level only for a Theme card); a number or a choice of levels for each terrain field the brush holds (Woods density and canopy height, Water depth, Road surface, Building weight, …); for an optional field the card offers (Water's Current, a building's Class) a choice that starts with None, which leaves the field out; and a family card's Type, which arms another member. A stamp or the DropShip blueprint has only its hint (the DropShip's Erase is its component's, with a radius); Sculpt holds its mode; Erase its radius. In Select it hides, and the selected object is edited in Edit. Precision mode belongs to painting and has its own row under the title; other controls wrap as complete widgets within the panel's width, which leaves room for the side view; where the board area is too narrow for both side by side (below about 1130 UI units of window width with the side view open), the Brush panel stands above the side view instead of under it. A brush taken from a stretched object with Use as brush shows its Stretch row (W, L and H; W and L for a decal), so the stretch every placed copy gets is visible and can be reset there; an unstretched brush has no such row. Theme uses a dropdown. Selecting or editing an existing instance preserves the paint template; Use as brush explicitly copies the selection into it. There is no Options dialog, Legacy Source control or Space paint category.
- Keys and gestures in one place: Z/X/C/V tools; click selects (a grouped object selects its group, a second click the member); a plain drag that starts on empty ground or on anything unselected draws a selection box, Shift+drag adds and Ctrl+drag removes (the box turns coral); dragging a selected object, inside a selected object's outline, or selected hexes moves the selection; Shift-click toggles objects, whole groups or hexes and Ctrl-click removes them; Ctrl+G groups, Ctrl+Shift+G ungroups; Ctrl+Z undo, Ctrl+Y or Ctrl+Shift+Z redo; Ctrl+C/Ctrl+V copy and paste hexes; Ctrl+S save, Ctrl+O open; Delete removes the selection; Ctrl+wheel changes the hovered hex's elevation; Ctrl at a Sculpt press inverts Raise/Lower; right-drag pans; Alt-click measures line of sight. Select's hint line repeats the box gesture. Menu → Help lists them all in the editor.
- The filename, unsaved marker and selected hex sit immediately right of the top-left toolbar as one white text line, for example `* Untitled board (0303)`, or `Picnic.board2 (imported, unsaved)` after opening `Picnic.board`, whose Save then defaults to that name next to the source, without a shaded background. Long lines truncate before the utility buttons. Action/error feedback uses a second line in that same space; while no hex is selected the inspector repeats it in full, so a long import summary stays readable. There is no bottom document strip or redundant editor title.
- The right column has the hex title and the Layers tools (Copy, Paste) over two regions with their own scrollbars: Layers (the hex's components, objects and groups) above Edit (the properties of the selected hex, component, object or group). A draggable divider between them keeps each region at least 60 units high. Until it is dragged, Layers take their natural height, up to 45 % of the column; a dragged position is remembered in the GUI preferences (`BoardEditorLayersSplit`). Refreshing values keeps Edit's scroll position; selecting an object, also in the 3D view, scrolls its row into view in Layers without moving Edit. Selecting a group (its row, or the board's first click on a member) highlights the group's row and keeps its members listed; selecting a member (its row, or the board's second click) highlights the member among all its siblings, expands its group if it was collapsed and scrolls the member's row into view. After a click on a row, Layers take the arrow keys (Up and Down move a highlight, Left and Right collapse and expand, Enter selects) until the board is clicked. A Layers row's tooltip shows its raw terrain codes as the board file writes them (`Terrain.toString`, for example `building:2:9`, the old editor's hover tooltip): the Ground row the whole hex, any other row its own component's terrains. Copy also puts the hex on the system clipboard as text (`Hex.getClipboardString`: the old `MegaMek Hex` text, or the `.board2` hex for one with appearance or objects); Paste takes a hex that another MegaMek window or a text editor put there since the editor's last Copy, otherwise the editor's own copy. The editor window gives the session the system clipboard; sessions that tests and tools create keep their copies to themselves.
- The editor's panels follow the published snapshot: they compare a new snapshot by value (and the installed anchors of the inspected hex, which are read from the terrain only with a new snapshot, while the terrain builds and in the frame after) and rebuild Layers and Edit, the Brush panel or the document line only when something they show changed. Layers and Edit also wait while a number is being edited, a row dragged, a choice list or gallery open, or a press on the board held. Card previews and the Settings dialog's theme result are updated from those changes instead of per-frame actions.
- Choose a visual design to browse the content blueprint. Building thumbnails are loaded only for the current page. Props and building assets without thumbnails get an asynchronous model preview; only one decoded preview is uploaded per frame. Each page owns its preview resources and releases them when replaced.
- Road surface and finish are linked through the blueprint: Paved and Alley use asphalt, Dirt uses dirt, and Gravel uses gravel. Painting, inspector edits and Use as brush all use that same mapping.
- A bridge's Edit panel has Built and Natural buttons under its fields: an explicit action to retype the whole connected bridge in one undo step. This differs from painting a Bridge card, which changes only the visited deck hexes and never silently retypes its neighbours (see Bridge types under Native files). A built bridge also has a Pillars toggle: concrete piers under the joints between the bridge's hexes, never at a hex centre (see Legacy scenery import for the rules). A natural bridge shows no Pillars toggle; switching to Natural drops the piers, and Pillars off leaves a built bridge. Built keeps the span's piers, on all of its hexes when any of them has piers (an imported span can have them on some hexes only).
- A pavement hex's Edit panel has an Edges row, Auto, Fitted and Hex, for how its walls and banks follow the fitted concrete outline of the 3D views (see Concrete fit beside placed objects): Auto (the default, stored as none) fits them straight or rounded except where a placed object stands on a wall the fit moves; Fitted fits them through objects and lists each object it cuts under Issues; Hex keeps plain hex steps. It is stored as the hex's `pavement` appearance (`pavement/fitted`, `pavement/hex`); the pavement brush has the same Edges setting, which every hex of a stroke gets.
- Choose an object in the library, then click a hex to stamp it. Each click elsewhere creates an independent instance; a click where the object's exact twin already stands (`BoardDecoration.twin`: the same model, name, colours and support, within 0.001 hex, 0.001° and the same scale) adds nothing and selects that twin with its group (`Already placed here - selected.`), and a drag skips twins. A stamp is placed whole unless every member already has its twin. Select props or decals in the viewport to drag them, or use the Contents list for exact position, rotation, mirror and scale. Shift-click toggles objects or whole hexes. Dragging the selection (a selected object, anywhere inside a selected object's outline box, or a selected hex) moves it in one undo step; a whole hex only moves when it was already selected. A drag that starts anywhere else, also on the sky or background around the board, draws a box: it selects the objects whose installed anchors (at their roof, deck or offset height) it covers, or, when it covers no object, the hexes whose centres it covers. Rail and maglev are terrain, so object box selection does not select them; edit them by painting, erasing or selecting their Ground or Bridge section. Shift+drag adds and Ctrl+drag removes, always of the current selection's kind (objects or hexes); a selection never mixes the two.
- Group (Ctrl+G) gives the selected objects, and every member of their groups, one new persistent group, saved in `.board2`, and selects that whole group. Ungroup (Ctrl+Shift+G) clears the selected groups. Each is one undo step, and both are in the right-click menu, which acts on the current selection. Clicking a member selects its whole group; clicking it again without dragging selects that member alone, and while drilled in, a sibling's click selects only the sibling. A click without a drag on one item of a larger selection (a box or Shift selection) narrows the selection to that item and its group; on a selected hex, a click on a placed object standing there selects the object, while a drag from anywhere on the selected hexes moves them. Shift toggles whole groups, and a box selects whole groups. A group may span hexes; there is no nesting, and a group with one remaining member acts ungrouped. With a whole group selected, the inspector moves (east, north), turns, scales and mirrors the whole group, and the tray turns, scales and mirrors it. These controls are relative to the group as it is: after every commit the moves and the turn read 0 and the scale 1, and Mirror flips the group. A live slider drag's value is its whole change so far and is one undo step. Turns, scales and mirrors pivot about the members' centroid in metric (pixel) space. Height offset, support, tilt, name and paint order are per member: drill in to edit them. Duplicate copies a whole group into one new group, overlapping the original, and selects the copy; a drilled-in member duplicates ungrouped. Contents show each group present in the hex as a `Group · N objects` header (`· M here` when it spans hexes; click selects the group, × deletes the whole group, as its tooltip says) with its members in this hex nested below. Its members stay listed while the group or one of them is selected: the selected row is highlighted, and a collapsed group expands when one of its members is selected (`UiTree`, see Layers above). A group's last remaining member is listed with its surface like an ungrouped object. Grouped decals are not drag-reorderable. Object anchors transfer to their destination hex on release, preserving world XY; surface-attached objects then follow the destination support. A whole-hex move previews before release, replaces destination hexes, and is rejected if any destination is outside the board. Attached props are grouped beneath their receiving terrain component.
- Group colours (b10-f1): a selected group's inspector shows the colour slots of its inspected member's model ("Colours of every member like this one"); a choice repaints that slot in one undo step (`Action.GROUP_VALUE` `colourN`) on the members like the inspected one: for a train's vehicle, every vehicle of its route kind (a stamped train's cars, whatever their model), so a stamped train is repainted at once; for any other model, every member of the same model. So the cars parked beside a converted maglev train, which share its group, keep their colours (b10-ffix). Route markers and decals keep theirs; a member whose model lacks the slot stores the colour without effect (the maglev gangway).
- Numeric captions are white and have two gestures: click to open a slider, or hold and drag horizontally to scrub immediately. Releasing a caption drag closes the slider and commits one undo step. Typed values commit on blur or Enter; Escape restores the previous value. `UiNumber.withCheckbox` embeds an optional checkbox before the caption, as used for brush Level. Slider ranges are convenient bounds, while typed values still use the document's validation. There are no numeric SET buttons.
- New props follow the clicked ground, bridge deck, building roof, industrial top or fuel tank, plus a height offset; a prop put down on a hex with ice stands on the ice. With Precision mode off, XY starts at the hex centre; enabling it uses the clicked position. Raising the supporting terrain raises the prop. A new placement gets an absolute (fixed) height only from a click in the air of the side view. Moving to a hex without the original receiver falls back to ground while preserving the offset. A ground prop never silently attaches to the highest nearby roof. One support rule (`BoardDecoration.Placement.level`) gives the level for all of them: absolute, ground, or the receiver's top, plus the offset. The editor, import and snapping measure the receiver's nominal top from the hex's rules terrain (`BoardEditorSnapping.level`), camera framing from the scene's support features, and the renderer settles on the drawn support mesh beneath the anchor.
- Hex section is in the side view, the board area's bottom-right corner panel. While open its header names the hex and the direction the section looks along (`HEX SECTION 0807 · looking N`); collapsed, it summarises the hex (`0303 · Ground L0 · 4 objects`). Its chevron, or Side view in the right-click menu, collapses and expands it. The choice is remembered in the GUI preferences (`BoardEditorSideView`), and when the board area is too narrow for an open side view beside a full Brush panel (as at 1280×800) the side view starts collapsed. The section is an orthographic side camera over the selected hex's installed geometry, looking along the main camera's yaw snapped to a hex side (the isometric view looks NW). Below the drawn ground the section is filled; a see-through liquid is only tinted down to its bed, so what stands in it (bridge piers, sunken objects) shows. It borrows the main renderer's models, materials, picking and terrain settings and owns only its framebuffer, which it renders again only when the document, the hex, the direction, its size or the installed geometry changes, and while the terrain builds. `GpuMapSource` keeps the previous editor snapshot instance while the session's state is equal (`Snapshot` is a record), so the side view and the editor panels compare snapshots by identity and do nothing on idle capture ticks (`GpuEditorSideViewSmokeTest` counts no new image over 30 idle frames). The left ruler is auto-ranged: one level below the lowest height, one above the highest or up to the tallest object, at least six levels, the whole hex across, with ticks every 1, 2, 5, 10, 20 or 50 levels at least 15 units apart. Each height of the hex has a dashed guide and a label pill in the right-hand column (`Bridge · L4`); alike items at one level share one pill (`Car · Blue ×2 · L4`: an object's label names its first replaced colour, so cars of different paints get their own pills and Layers rows), and the pills keep the order of their levels without overlapping. The column is bounded by the side view: items above or below the plotted range gather in one dimmed chip at its top or bottom (`3 above`, `2 below`), which has no guide and never moves the other pills off their guides; when the column is too short, all objects at the busiest level share one pill (`12 objects · L0`), and the highest pills that still do not fit join the top chip (`4 more`). The hint line under the plot has its own plain backdrop. The heights are the session's (`Snapshot.levels`, nominal levels by the shared support rule): the ground (the hex level; on a water hex the water surface), the water bed, a bridge deck, a building, fuel tank or industrial top, a canopy, and each placed object; a decal lies on its support, so its pill has no grip. Dragging a pill, or the geometry itself, moves that height through the session's HEIGHT command, one undo step per drag, in whole levels (Ctrl: quarter levels for objects): a deck moves the whole bridge span and a building's or fuel tank's top the whole structure (joined through the structure's exits; each hex gets the height that gives the same top, within the field's range), the water bed changes the depth, an object its offset above its support or its fixed level. Releasing the pointer is the commit; losing touch focus keeps the last previewed height. A pill that stands for several items moves all of them in the same drag (one undo step); a click on a pill selects its item, or its objects as a box would, whole groups included. With a prop or decal card armed, the section shows where a click puts it (PLACE): on a guide within 8 units, on that support at the brush's offset (ground on an ice hex is the ice, as for a Paint click); elsewhere, for a prop only, at that fixed level. The position along the view becomes the object's offset in the hex. A placement is one undo step and selects the new object. Hovering a pill, an item's geometry or a Layers row highlights that item in all three places: its pill, its Layers row and, for an object, its box on the board; a shared pill highlights every item it stands for; an object under the board pointer in the inspected hex highlights its pill and row. Reveal, in the header, isolates and fits the selected prop. Pills show nominal levels; the image shows where the renderer settles an object on the drawn support, which can lie slightly higher on uneven ground.
- Contents rows include a borderless red remove button. Drag an object's grip to reorder it among objects on the same receiving surface. Higher decals in the list paint over lower decals; typing Paint order uses the same ordering. Prop list order survives saving, but physical height still determines overlap. Use Hex section to move a prop vertically.
- Paint markings target one named receiving surface and have an explicit paint order. Their footprint can be rotated, translated, mirrored and scaled. Newly placed decals span neighbouring hexes by default; turn off Span neighbouring hexes to clip to the owner. Each recipient projects onto the selected kind of surface and uses the same UV transform. Decals have no arbitrary vertical offset. Props can also extend beyond their owning hex.
- Opening a legacy `.board` imports its scenery (see Legacy scenery import under Native files): every picnic table, car, tree, bevel or pillar becomes its own object, and the objects one legacy artwork showed form one group (pillar art on a bridge hex turns on the bridge's Pillars toggle instead), and every bridge gets its type, built or natural. Stamps (Roadside trees under Transport, Tree cluster 1–5 under Parks and furniture) paint a scenery layout the same way: one click places its members as one new group with fresh IDs, as one undo step, and selects that whole group. Roadside trees follow the hex's road exits and need a road. Stamps have no live preview and no brush options; select a stamp's group to edit or delete it.
- Every placed object is one mesh; a composition is placed as separate objects (import, stamps), and no palette prop's ID is a `layouts.json` key. Transport offers the two routes, Maglev and Rail (below), the crossing signal and the Roadside trees stamp, and the Level crossing among its decals; Maglev and wagons offers the station platform, the city and colony maglev cars, the thirteen rail vehicles of three families (Frontier freight, Express passenger, Ironline colony freight) and five train stamps (City maglev, Colony maglev, Freight train, Express train, Colony train), every vehicle with Body and Trim colours. A vehicle or train stamp placed on a hex that holds a route of its kind rides it: it snaps onto the nearest drawn track (`RailRoute.snap`: its pieces, stubs and dead ends; the nearest compatible ground or deck route, using its corridor placement), turned along it, at its ride height (a rail vehicle and a buffer stop on the rail top the track draws under it, on ballast or set into a road, which the renderer adds in model px as it builds the track, `BoardRail.railTop`, so it stays on the rails at any Base level height; the maglev's beam), and a stamp's vehicles stand their row spacing apart along the track from hex to hex (`RailRoute.follow`, onto dead ends' runs and stubs too), each riding the marker it reaches and belonging to that marker's hex, so the wagons that run onto a bridge deck ride the deck. A stamp places only the vehicles that fit on the track (b10-f3): a vehicle reaches half the way to the nearest other car of its train on each side of its centre (a maglev coupler, which rides between two cars, is not counted as one, so it never halves their measure), and both ends must lie on the track (`RailRoute.OnTrack.beyond` is 0); the stroke notice then says "N of M vehicles placed"; without a route it stands on the hex's support as any object. Magnetic snapping is blueprint-defined for concrete parking barriers; connectors must face one another and match height and scale. Dragging previews the destination while retaining the selected ID and original owner until release. Elevated drags retain their rendered anchor plane and show the ground projection used for the final drop. A selected object's outline is its own box; the hex-shaped ground projection appears only while the object is dragged, so a roof object's outline no longer spans its building. A selected decal's outline is the flat box of its paint over every hex it covers (`GpuTerrain.editorObjects`), so a clicked decal shows selected as an object does; unlike an object's outline box, its box does not take presses, only its paint does, so an object standing on a selected decal stays clickable. Water is see-through for object picks: a click through the surface takes the object or decal beneath it, down to the bed (molten lava stays opaque, `GpuTerrain.decorationHit`); a click on open water still selects the hex. The game needs no such rule, since a unit takes a click by its drawn model before the terrain (`GpuBattleView.pickSelection`), so a submerged submarine is clicked through the water in the 3D and Tactical views. With the Select tool, one selected object or decal, or one whole group, has a rotation handle beside its outline: a short line from the middle of the outline's right side, as the camera sees it, to a small circle, a fixed size on screen. A drag on the circle turns the selection about the vertical axis through its anchor (a group about its members' centre, as the Group transform's Turn does) in whole degrees, one undo step per drag; the pointer is a hand over the circle, which takes any click within it. A selected object that does not rest on its support (a positive offset, a fixed level, or a missing support) hangs on the airborne-unit tether, from its drawn anchor down to the support or to the owning hex's level, while dragged too. The white hover outline rises only to levels a unit can stand on, in the game and the editor alike (`GpuTerrain.walkableHit`): the ground or water surface, a bridge deck, a building's storeys and roof; placed objects, trees, industrial cover and fuel tanks are looked through. The side view and the inspector stop an object one level below its hex's floor (`BoardEditorSnapping.lowestLevel`).
- Cliff tops are six directional buttons on ground. The shared rules admit manual cliffs at drops of one or two floor levels; larger cliffs are automatic. Elevator controls expose die rolls or shaft height/capacity instead of packed integers. An industrial elevator's Edit fields are Shaft bottom level (the terrain level), Shaft top level and Capacity (tons), with the old editor's tooltips and help text; the palette card and Add property both give a shaft from the surface that carries 100 t (`industrial_elevator:0:10` in the blueprint), and the shared rule refuses a bottom above the top. A deployment zone's IDs are its terrain's exits mask, zone n in bit n − 1, read as the game reads them (`Board.exitsAsIntList`, which `Board.initializeDeploymentZones` uses): the Deployment zone card (Scenario features, `deployment_zone:0:1`, zone 1, as the old editor wrote it) has a **Zone** number 1–31 in its Brush panel; Paint adds that zone to every footprint hex and keeps their other zones, and Erase with the card removes only that zone, the terrain going with the last one. Edit shows the hex's **Zone IDs** (`1, 3`) instead of the unread level; IDs outside 1–31 are refused and an empty list removes the zone; Add property gives zone 1. The hex stamp, Copy/Paste and Delete carry a hex's zones with the whole hex (the old eyedropper stripped them).
- Terrain painting applies the active recipe, preserving other components and objects. Additive categories such as Hazards preserve unrelated properties within their category too. Ground brushes preserve elevation and theme unless enabled in Brush options. Erase removes the active recipe's component or matching objects. **Only overwrite clear hexes** (the old editor's option, in the Brush panel of terrain cards, hex stamps and Sculpt) limits them to hexes without terrain (automatic markers, level and theme do not count; this is not the rules' clear hex, `Hex.isClear`): the brush preview leaves the other hexes out, and Sculpt's Slope does not step them either. Erase and object placement are not limited (the option is not shown there). A drag is one undo step. Copy/paste and duplicate allocate new object IDs. Ctrl+wheel directly adjusts only the hovered hex in every tool, including Sculpt; Ctrl+Z/Y, Ctrl+C/V and Ctrl+S/O operate the native session. Delete removes the selected objects or hexes.
- **Paint and Erase preview (b10-f2).** Before a click, Paint and Erase show at the pointer exactly what the click would do, computed by the click itself: `BoardEditorSession.preview` runs the pointer event and its stroke's completion (`completeStroke`: a hex stamp's joined route sides, implicit-deck reconciliation and explicit bridge-exit freezing, as `finishStroke` runs them) on the document without telling the board's listeners (`Board.quietly`), records each hex it changes, and puts back the hexes and every stroke field, so nothing else sees it (no tile is recaptured, no chunk rebuilt, no undo step, revision or selection changes). Every placement rule therefore holds for the preview too: precision mode or the hex centre, the magnets, the support under the pointer (a roof, a deck), rolling stock riding a route, a stamp's members along the track, the brush radius and Only overwrite clear hexes. The preview is kept until the document, the brush, the hex or (for an object placed precisely) the pointer's place changes. The render thread reports where a press would land, the same hit a click takes (`BoardSource.editorHover`); the EDT turns the preview into what it draws (`GpuEditorPreview.Data`), and the view draws it over the finished frame, after the hover rings: the hexes the click changes ringed white (Erase red) inside the brush's dimmed reach; new or changed objects as translucent ghosts in their colours, placed by the drag preview's own placement (`GpuTerrain.editorHeight`, also `previewEditorObjects`'), routes built by the route builder on the step's tiles (`GpuTerrain.routeGhost`), a decal's paint projected as a chunk projects it (`decalGhost`); a terrain card's result as flat stand-ins of each changed hex, never its materials: a top at the result's level, water down to its bed, a structure or canopy as a volume to its height (the blueprint's height fields), a deck at its height and a changed road's or bridge's centreline to its exits, tinted with the result's minimap colour (`GpuMinimap.colour` of the hovered hex's result, `BoardTiles.preview`); and a label at the hex with what the click brings (the hex card's names, zones by their IDs). Erase shows what goes in red: the removed objects as red ghosts with red boxes, the terrain or component as red stand-ins of the hex as it is, and `Removes …`. While a rail, maglev, road or bridge is drawn by hand (below), the preview is the whole route as its release builds it plus the next step: once the pointer is in the path's last hex and has moved more than a fifth of a hex since it took it (or pressed in it), the side its movement heads for (`BoardEditorSession.heading`; the pointer's place alone would mislead, since just inside a hex it still lies in the half it came in by) names the next hex, and the ghost includes the step into it (the gentle piece, or a tight step's stubs, the next hex's run and its buffer stop); while an Erase route stroke is drawn, the preview is that step alone; other strokes show no preview. At most 200 object ghosts are built (a wide hex stamp shows its footprint and stand-ins only). Cost, measured on 2026-10-11 in the editor view of Valencia (1600x1000, isometric, a radius-20 brush whose 1,141 hexes cover the board area) for each of 96 terrain cards (every preset, every design but the building designs, of which five stand for 3,351, and nine themes), frame by frame with and without the stand-ins (100 frames each): the RTX 4070 drew 5.4 ms frames, the stand-ins cost +0.05 ms (median; at most +0.34 ms, within the method's A/A spread of 0.45 ms); the Iris Xe drew 33 ms frames, +0.44 ms (median; at most +2.8 ms, as large as its A/A spread, and the four highest cards measured again with 300 frames each cost +0.08 to +0.86 ms). No card is slow, so every terrain card keeps its translucent stand-ins. The EDT computes a new preview when the hovered hex changes: 19 ms (median, RTX 4070 run; at most 45 ms, a bridge card) and 3 ms to convert it; the render thread builds its mesh in 2 ms (at most 12 ms). Limitations: that EDT time grows with the brush's hexes and is felt as a short delay of the panels, not of the board, while a radius-20 brush moves from hex to hex; the stand-ins' tint is the hovered hex's result, one colour for the footprint; a volume's sides show through scenery at reduced opacity.
- **Routes drawn by hand (route-drag, the user's design of 2026-10-11).** Paint with a Rail or Maglev brush or the Road card draws the route by hand: the press sets its start, each hex the drag enters becomes its next waypoint, and only the release builds it, as one undo step, so the user can fix the route before it exists. The waypoints are `RoutePath` (package `boardeditor`): stepping back into the hex before the last waypoint takes that waypoint back (again and again, along the path); entering any other hex of the path adds it again, so one stroke may cross or loop over itself and the route rules make the crossing; a move that skips hexes fills them with a straight hex line from the last waypoint (cube coordinates, so a move along a row takes no zigzag; where that line runs exactly between two hexes it takes the one on the board, and the previous waypoint over the other, so a fast move back along the previous hex's border retraces alike in every direction). A hex is taken once the pointer is in its core, within 60 % of the way from its centre to its sides (`BoardEditorSession.core`), so a pointer that grazes a hex's corner adds no waypoint there and no sharp turn (a graze during an edge scroll had left two stubs in the middle of a straight rail). A hex the pointer crosses only by its border on its way to a hex two from the path's end is taken when the pointer lands there, so a bend goes through the hex the pointer went through, not the other one beside both ends; and the release builds the route on into the hex the pointer is in, taken or not, as the preview, its rings and its length show it (`buildDrawing`). Until the release the document is untouched (`BoardEditorSession.draw`); the release (`finishStroke`) plays the waypoints through the stroke code that painted them before (`event`: the route's markers, steps, joins and refusals, or the road card's footprint in each hex), so a route that starts or ends on existing track or road continues and joins it by the existing rules (junctions, stubs, automatic road exits), and a click without a drag places a marker without sides or paints the radius as before. Esc or a right click during the drag drops it with no change (`cancelStroke`; the view checks them before the HUD's Esc chain), and so does the window losing the focus or a modal menu opening (`BoardInput.interrupt`), whose release never reaches the view. Other keys during the drag reach only the camera's binds: a hotkey or an editor command (Undo, a tool key) ends the stroke, which would build the route before its release. The preview (`preview`) is the whole route as the release builds it, run unseen as above: the route builder's track ghosts or the road's centreline stand-ins, white rings on the path's hexes, a label with the brush or road name, the length in hexes (a crossing hex counts each time) and the reason a hex or side is left out (a side another route owns); every hex where the release would leave a route side ending in a stub (`Preview.stubs`: a new stranded side by `RailRoute.stranded` of the sides the builder draws, the 120-degree turns) is ringed red twice and its ghost is red. The step the pointer heads for past the path's end (batch 10's direction ghost, `Preview.next`) shows too, but a release does not build it, so its side is left out of the red marks. Holding the drag within 48 px (scaled) of the edge of the board area the panels leave free (the area Fit board frames), or past it, scrolls the board that way, faster the nearer the edge and at most at the keyboard's scroll speed (`GpuBattleView.edgePan`, `BoardInput.autoPan` through the camera's own pan), except over a panel, where the drag sends no events and the board stays; the route follows the hex then under the pointer through the drag's own picking (`editorPointer`); while a route is drawn the camera's re-pick at the cursor leaves the hover and the preview's pointer to the drag (LWJGL sends no mouse-moves during a drag, so `editorPointer` sets the hover), and the route keeps showing with the pointer past the board's edge and once the drag comes back. Cost on the EDT (unit-test JVM, 64 x 64 board): the whole-route preview of a 75-hex route takes 4 to 6 ms per new hex (rail 5.3, maglev 5.6, road 4.1 ms at 75 hexes; about 1 ms at 10) and its release 3 to 9 ms. Limitations: a route of more than 200 objects (markers and buffer stops) shows its rings and label without ghosts (the preview's ghost cap); the edge scroll uses the framing area, whose bottom edge is the taller of the Brush panel and the side view, so near the bottom it starts above the open strip between them; only English texts for the new and changed message keys.
- Sculpt changes ground levels only; terrain, water, bridges, buildings and objects in a hex are kept. Its Brush panel holds the shared Radius, `Raise | Lower | Level` and Slope (on by default). A click moves every footprint hex by one level; a drag moves each footprint hex once, when the stroke first enters it. Ctrl at the press inverts Raise and Lower. Level sets every touched hex to the level of the stroke's first hex. With Slope, neighbours are then stepped toward the moved hexes until no edge differs by more than one level; an edge that was already steeper than one level before each step stays a cliff, and no neighbour moves away from the source. Slope can move neighbours outside the footprint, including the water surface of an adjacent water hex and the base of an adjacent bridge or building hex. Slope off leaves plateaus with cliffs. Ctrl+wheel always changes only the hovered hex, including in Sculpt mode, regardless of brush radius, Raise/Lower/Level mode or Slope setting. It never cascades into neighbouring hexes. One stroke, or one Ctrl+wheel gesture until Ctrl is released, is one undo step. The rule lives in `LevelSculpt`; `BoardEditorSession` applies its levels through the ordinary hex edit, so exits, inclines and cliff tops are derived as for any other level change. A fast drag also covers the hexes between its pointer events. Limitations: the hover hint (for example `Raise · 7 hexes` or `Level to L2`) shows the tray mode and does not flip while Ctrl is held. Wheel notches captured within one 33 ms refresh are replayed in arrival order against their captured hovered hexes.
- Issues: a plain red warning triangle at the top right, left of the camera buttons, appears only while the board has issues; its tooltip counts them. A click lists them, for example `1814 · Incomplete Bridge! …` (at most 200 rows, then a count of the rest); choosing one switches to Select and selects the hex, or the object the issue is about, then frames that hex in the board area between the side columns, below the toolbar and above the corner panels as Select lays them out (it has no Brush panel). Issues are the game's own rules through `Board.hexErrors` (each hex's `Hex.isValid` plus its building-exit checks: the per-hex step of `Board.isValid`, extracted so both use one implementation), placed objects whose art is missing (a prop with neither a catalog entry nor a model file, a decal without its image under `models/board/decals/`), objects whose support (roof, deck, industry, fuel tank or ice) is gone (`Object on deck but no bridge`), what the legacy import of the open document could not decode exactly (an emblem set with pieces missing), while that object stays in its hex, objects inside a concrete wall of a Fitted pavement hex (`Car stands inside a concrete wall (Edges: Fitted)`, read from the 3D board's installed fit, so after its terrain build), and stacks of exact twins made before (`3 identical copies of Car`, at the first copy), for which the list offers **Remove identical copies**: it keeps each stack's first object and its group, in one undo step. Loading, a new board and opening validate every hex; each committed edit (the commit that makes an undo step), undo and redo re-validates only that edit's hexes, which already include every changed hex's neighbours, and the snapshot publishes a new list only then, with no per-frame work. Issues never block saving (user decision P, 2026-10-10, as the old editor did): before a Save with rules errors (`Board.isValid`, the same rules) the old validation report lists them, "The following invalid hexes were found in this board", and the board is then saved; the issues header says so (`Saving works; games refuse rules errors`). The editor reopens such a file and lists its errors again (Open reads with `BoardFile.read(path, true)`, the "continue on error" mode of the old `board.load(is, null, true)`; the Open message counts them). Every other reader stays strict: a game's sheets, the lobby's board preview, scenarios and the map preview (`BoardFile.loadSheet`) refuse a `.board2` with a rules error exactly as they refuse an invalid `.board` (both go through the one reader, `BoardFile.read`), and random and surprise map selection skip it (`MapSettings.replaceBoardWithRandom` catches the strict reader's refusal and drops the board from its candidates). The callers of `Board.load(stream, errors, true)` that continue on errors for an old `.board` (the lobby's map list and map buttons, which mark the board invalid, the advanced search's table and the board tagger, which skips it) get the same for a `.board2`; the advanced search reads only the chosen board's size. `BoardFile.write` no longer checks the rules: the readers decide. Since parity batch A the shared rules also check an industrial elevator's shaft (its bottom, the terrain level, must not lie above its top), so the issues list shows such a hex, the editor refuses the value, and a game never loads such a board. Timing, measured with the opt-in `BoardEditorValidationTimingTest` (`MEGAMEK_VALENCIA_TIMING=1`) on the largest shipped board, Valencia City (128 × 192 = 24,576 hexes, 0 issues) on this development laptop, two runs: a full validation takes 6.7–18.9 ms (medians 8.7 and 9.4 ms over 20 runs each after warm-up) and 18.8–18.9 ms the first time after opening (cold model-file lookups and JIT), next to 1.1 s for reading, importing and validating the board. That is under the ~30 ms EDT budget, and only loading, a new board, opening and a whole-map theme validate everything, so validation runs synchronously on the EDT; there is no worker, debounce or cancellation. The Settings dialog no longer has a Validate button.
- Settings at the top right has three sections in one scrolling dialog. **Map** holds the board's own settings: **Arena** (the tag `Arena`, `BoardClassifier.ARENA_TAG`, which keeps the board out of normal random map selection), **Exit Roads to Pavement** (`options.exitRoadsToPavement`; every hex derives its exits again at once) and **Tags**: the manual tags as chips with a remove button beside an Add tag field, and the automatic `… (Auto)` tags, muted and read-only, with **Update automatic tags** (`BoardsTagger.updateAutoTags`, the one rule the board tagger also uses). Like the old editor's checkboxes these are no undo steps (the control is its own undo); they mark the document unsaved. **Whole board** holds the commands over every hex, each one undo step through the session's one helper (`everyHex`, which installs all changed hexes together so manual cliff edges survive): the global theme picker (it changes all hexes, including their previous theme overrides), **Raise/Lower Board** by a number of levels (it also moves the Solaris elevator's alternate level, an absolute level, and objects placed at a fixed level; depths, heights and industrial elevator shafts are relative and stay), **Flatten** (every hex to L0, by the same rule), **Flood the Board** (below), **Remove…** (a component that some hex holds, from every hex, with its appearance; objects stay) and **Clear Board** (after a confirmation, every hex blank, as Delete blanks a selected hex). **Flood** uses the old editor's rules: a hex below the surface level gets water up to it on top of the water it had and its level becomes the surface; hexes at or above it stay. With **Remove submerged terrain** a submerged hex also loses every other component, its appearance and its objects, except a bridge whose deck stays at or above the surface (its height becomes deck − surface; the objects on its deck stay) and its deployment zones, which are scenario data (the old editor deleted them). The session's messages (a command's result, a refused tag) show in the dialog's status line under the sections. The commands run on the EDT: on Valencia City (128 × 192 = 24,576 hexes) a Flood or Raise/Lower of every hex took 0.26–0.37 s, Clear 0.18 s and the global theme 0.47 s, and each Undo 30–110 ms (one run each, in the unit-test JVM with coverage; scratch `ParityAScratchTimingTest`). An undo step's maps are hash maps, not `Map.copyOf`: `Coords` hashes collide in runs, and `Map.copyOf`'s probing had made each of these take over 2 s. **Size** has **Resize Map**: North, East, South and West amounts (a negative amount cuts that edge; the old Resize dialog's labels, tooltips and odd-west note) with the resulting size, and the button, which closes the dialog. Resize (`BoardUtilities.resize`, the old editor's placement rule) moves each hex by the west and north amounts, and an odd column one row further when the west amount is odd, so every hex keeps its neighbours; hexes outside the new size are dropped and new hexes are blank. Each hex keeps its terrain, appearance and objects with their groups, and the board its tags, Arena flag, roads option, description, type and header; notes move with their hexes (the old resize lost the tags, the option and the description). It is one undo step that swaps the whole board (a new board of the game, so every view follows it); Undo and Redo keep the board settings that are no undo steps (tags, roads option) as they are, and Save's file stays the document's file. Below it, **New board** creates a blank board of the given dimensions, and **Random map...** opens the existing random map generator dialog (`RandomMapDialog`, as the old editor's New did) for a board of that size, which then becomes the document through New's path (save prompt, conversion, validation). Tuning opens above the workspace; Settings and Tuning close each other. The editor camera uses the full viewport, including space behind panels. Picking assets or changing panel sizes never reframes the board. The explicit Fit board button and a framed issue account for the currently visible area between the panels, above the corner panels. The UI scale reduces when needed to fit a smaller window.

Native GLB props retain their alpha-tested cutout and mirrored-face settings through all render passes. Plant material roles use the existing foliage shader; visual props do not acquire building cutaway behavior merely because they share a hex with a structure.

**Roads, bridges, rail and maglev:** each card draws a one-hex-wide route. Its Brush and Erase panels share **Height: Follow / Level**, **+N** (0–50) and **Pillars**. Follow +0 uses dry ground and follows its hills; entering water at depth 1 or more, including ice, holds the last surface height and creates a deck where needed. Depth-0 water and magma use the ground rule. Follow +N raises the route N levels above each hex. Level +N holds the press surface plus N for the whole stroke, meeting ground only at that exact level. Rail, road and bridge cards default to +0; maglev defaults to Follow +1 with pillars. The readout and preview use the same layer decision as the command: Ground, an existing Deck, New deck, or a refusal. A second deck, a deck through a building or fuel tank, ground above a fixed route, and a missing exit on an explicit bridge are refused without changing that hex.

An existing deck within one level is used when the pointer hits it, the stroke is already elevated, or no dry ground is available. A Follow +0 route leaving a deck lands on dry ground within one level; otherwise it stays at the deck height. A road or rail stroke creates only the implicit deck it needs. Its exits are the union of its deck ways, and removing its last way removes that implicit deck. Rail and maglev start with a Hardened bridge (CF 650); roads start Light (CF 40), inheriting a connected deck's strength and pillars. Bridge cards create explicit, clean decks: the first and last dry bank hexes are landings, not deck hexes. Painting a way on half a bridge changes only the visited hexes. Painting a bridge card changes only its visited deck hexes; choosing Built/Natural, Standard/Truss or Pillars explicitly in Edit remains a whole-span action.

**Ground and Deck editing.** Ground holds its own Road and Rail rows; the Bridge section holds Deck road and Deck rail. Their six edges, rail/maglev kind and junction layout edit that layer. **On deck** and **Beneath** move a way between the ground and the existing deck in one undo step, refusing an occupied destination or exits outside an explicit bridge. Removing a deck removes its deck ways and keeps the ways beneath it. Erase follows the same Height/layer rule as Paint, cuts the connected neighbours' reciprocal ends and removes only the armed rail kind. Erasing a way from an explicit deck leaves the clean deck. Flood removal preserves ways on a surviving deck. Copy, paste and whole-hex moves keep the terrain and appearance together and reconcile route ends at the edited boundary.

Rail and maglev share `megamek.common.board.RailRoute` and `BoardRail` in every view. A stroke records each entrance and exit: opposite sides form a straight, sides two apart a gentle 60-degree arc, and adjacent sides end in stubs rather than a tight turn. Parallel strokes stay apart; drawing over a route adds the path just drawn. Ground rail follows the road-shaped ground and deck rail follows its deck. Where a road crosses the track, its rails are set into the road; where road and rail run together, they form a corridor as below. Rail dead ends have generated buffer stops; maglev ends have a beam cap. Each stroke, edge edit, junction or layer change is one undo step.

**Junctions.** A route lays only gentle pieces: straights between opposite sides and 60-degree arcs between sides two apart. Of the 64 side masks, 18 have more than one sensible layout. When the drawn layout differs from the default, its `rail` or `bridgeRail` appearance owner stores `tracks`. The **JUNCTION** card opens the mask's named layouts seen from above (`RailRoute.junctions`); a pick is one undo step. A side without a gentle partner ends in a stub with a buffer stop. **CORRIDOR · Middle / Beside** changes a compatible road-and-rail run on the same ground or deck layer. Middle, the default, puts the track on ballast between two 2.8-metre road lanes. Beside shifts the road and track to opposite sides; **Swap side** reverses them for the connected run. Corridor changes use the common route geometry and re-snap vehicles already riding that run.

**One ground and one deck.** A hex can carry one ground way layer and one bridge deck, each with its own road and rail. Rail and maglev are the two kinds of the same rail terrain, not separately stored objects or extra floors. Their rendered route markers are derived from terrain. Clicking a route selects its Ground or Bridge section; it is not a draggable object or group member. A second elevated maglev deck over the same hex is refused.

**Pillars.** Pillars belong to the bridge carrying the way, including an implicit bridge created by a maglev stroke. The brush's Pillars option applies when it creates a deck; the Bridge inspector changes a connected span in one undo step. A maglev-only implicit deck draws its narrow guideway beam with optional slim pillars, without an ordinary bridge slab or landings. Turning Pillars on or off preserves that implicit guideway type and its height. A clean or mixed-use built deck uses the ordinary bridge geometry. Both use the shared support room rule; pillars are not placed through another supported route or a building.

The saved route data is terrain: `rail:1` / `bridge_rail:1` for regular rail and level 2 for maglev, with explicit side masks N=1, NE=2, SE=4, S=8, SW=16, NW=32. `bridge_road` stores the deck road's surface and explicit exits. Ground roads keep their automatic-exit rule. `rail` and `bridgeRail` appearance hold optional junction `tracks` and corridor `beside`; `bridgeRoad` holds only the deck road material. Implicit decks are marked `bridge/implicit` or `bridge/implicit-pillars` in the bridge appearance. No author-created rail or maglev route marker is stored in `decorations`. A board flip transforms terrain exits and the appearance layout together. Rendering derives its route descriptors from these values; geometry changes with board edits, not camera movement. Maglev transitions and rail pieces use the same common route model as rolling-stock snapping. Rolling stock is placed scenery: there is no train simulation.

Undo captures neighbors affected by an edit as well as the painted hex. Board batches install all replacement hexes before deriving exits and cliff bottoms, so an undo cannot erase a restored neighboring cliff during initialization.

## Native files and compatibility

`BoardFile` reads both legacy `.board` and native `.board2` documents. Native JSON requires `format: "megamek-board"` and `version: 2`. Unknown fields, unsupported versions, malformed terrain, duplicate coordinates and duplicate object IDs are rejected. Failed loads leave the active document intact.

Version 2 is still under development; the scale/overflow work extends version 2 rather than introducing another format. For a decal, omitted `clipToHex` retains the earlier owner-clipped behaviour and omitted `scale` means 1. The current writer emits an explicit `clipToHex` value for every decal. New editor brushes use `false`. An earlier version-2 reader that does not recognize this field rejects the file instead of silently dropping it.

Every hex has explicit one-based `[column,row]` coordinates. After the `MegaMek Hex2` header line, the deterministic writer puts one hex on each physical line, including ordinary hexes:

```json
{"format":"megamek-board","version":2,"size":{"width":2,"height":1},
"hexes":[
{"elevation":0,"at":[1,1]},
{"elevation":0,"terrain":"road:4:9","appearance":{"road":{"material":"gravel"}},"at":[2,1]}
]}
```

Gameplay terrain retains its existing compact string representation. `appearance` holds visual choices owned by terrain components; a vegetation look may store `rotation` (clockwise degrees in 30-degree steps, 30 to 330; no rotation is not written), which turns a container yard look. `decorations` holds independently identified visual instances. Neither introduces movement, cover, building floors, or additional gameplay bridges. Physical placement determines depth; array order does not stand in for height.

Imported terrain selectors, themes, descriptions, tags, annotations, board type, road-to-pavement option and leading source comments are preserved. A board without leading comments of its own (a new board) is saved with the CC BY-NC-SA license header and the year (`Board.licenseHeader`, shared with the legacy writer) when the Client Settings' "include license" option is on, as the old editor did. The editor's Open, Save and Save As, and the Menu's **Recent Boards** entries (the Menu also has **Run Board Tagger**: the board tagger rewrites the automatic tags of every board file in the boards directories off the EDT, its entry disabled meanwhile, then the open document gets the same automatic tags and the old report says it is done), add the file to the Recent Boards list that the launcher also shows (`RecentBoardList`); the session's plain `open`/`save`, which tests and tools use, leave the list alone. Save games keep every placed object's colour slots (an XStream converter for `BoardDecoration.Colours` in `SerializationHelper`; before it, XStream rebuilt the slot list wrongly and every object lost its colours in a saved game). Legacy printed hex labels are not reinterpreted: migration follows the old loader’s actual record order and note coordinates. Unresolved asset keys are retained. Missing prop meshes use a visible placeholder; missing paint is retained without painting a substitute surface.

Opening a legacy map does not make its original path the save destination. The new editor saves `.board2` only. Saves check object identities (a board that breaks the rules is saved, see Issues), write an adjacent temporary file, and replace the destination atomically where the filesystem supports that operation. Dirty state and the active path change only after success. The distinct extension and incompatible header keep native documents away from older applications; do not rename them for one.

**2D views of `.board2`.** The 2D Swing views load `.board2`: the lobby's board preview, 2D gameplay and the editor's 2D Preview. They show terrain only, draw no objects and give no warning about 3D-only content. A game, the lobby and a map preview that load an old `.board` convert it and keep its legacy scenery tokens in memory, so their 2D views still draw the old sprites. A `.board2` never holds a token the conversion took: `BoardFile.write` leaves them out (`BoardSceneryLayouts.withoutTakenTokens`, the same "taken" predicate as the conversion), and writing an unconverted board that holds one is refused. The editor's document holds none either: opening a board drops them after the conversion. The Edit panel shows no Fluff field (fluff fields are skipped, and Add property does not offer them), so no control types such a value; as a safeguard, a Fluff value that a session command leaves on a hex (the `TERRAIN` command still accepts one) and that names converted art becomes its objects and loses its token when the edit is committed, in the same undo step (Undo returns the hex as it was before the value was set). So the 2D Preview shows what a 2D player of the saved `.board2` sees: rule terrain, including an imported car park's lane road (the tileset's `road:1:<exits>` image), and the art of its designs, but no sprite for art that became objects. Since batch 10 the conversion takes every legacy art token (below), and the game's 2D tileset draws a hex's designs as the tokens they stand for (`HexTileset` of a game matches the hex merged with every owner's design selectors, `BoardEditorBlueprint.artwork`): building art, transitions, kerbs and horizontal road pieces, orchards and rough look in the 2D board of a `.board2` as in that of its `.board`. Decals, rails and other objects have no 2D sprite there. Since b10-f3 that includes the 108 building hexes whose art is a building model's asset design (each such design carries the selector of its art, `fluff:11:1`-`8`, `fluff:1` or `fluff:3`; `reproducing` never picks an asset design by its selector, the model decides) and the 66 quay hexes (quay art becomes `ground/quay-1`-`8`, which only the 2D board draws: the 3D views derive the fitted quay wall).

**Legacy conversion (batch 9).** Every place that loads an old `.board` for a board to play or to look at converts it with one function, `megamek.common.board.BoardSceneryLayouts.convert`: image-free common code (no AWT, any thread, a headless server included) that resolves each hex's scenery with the 3D tileset's text matching (`TilesetScenery.resolve`, on the matcher the 2D tileset also uses, `TilesetMatcher`) and turns every decodable artwork into the objects of its `layouts.json` rows. The load sites: a game's map sheets on the server, each sheet converted after it loads and before it is flipped and combined (`BoardFile.loadSheet`, used by `TWBoardTransformer` for the game start, Generate battlefield and autoresolve, by `ServerBoardHelper` for the lobby's board preview, by `ScenarioV1`, and by `BoardDeserializer` for scenario v2 and SBF; random sheets are converted as they are generated); an old saved game's boards when it loads (`Game.initializeAfterLoad`); the map list's and the advanced search's preview (`GpuBoardWindow.loadPreview`); and the editor's Open and New. Every client, 3D or 2D, receives the server's converted board; a client never converts a game board. The lobby's deployment-zone probes read only size and edges and do not convert; board thumbnails, the advanced-search table, the board tagger and the validators read files as they are. The editor calls its conversion an import and reports it (below). Meshes live in topic folders of `models/board/scenery/` (`roofs/`, `parks/`, `pools/`, `vehicles/`, ...), never at a legacy key, so even a plain renamed mesh decodes through one row; the old-to-new table is in mm-data's `data/models/board/README.md`. Rows are model pixels; objects store them in hex width/height units. Broad park tree rows draw their species and heading from the hex's seed, as the old render did. IDs are `L<x>_<y>_<n>` (deterministic, so the server and every client convert alike and re-importing gives the same `.board2`), and the objects of one artwork form one group `L<x>_<y>_g<k>` when there are two or more. Objects stand on the hex's roof, bridge deck, industrial top, fuel tank or ice, otherwise on the ground; the trees of a road passing under a bridge stand beneath its deck (art on a bridge hex stands on its generated deck, including flat built decks), and pillar art on a bridge hex turns on the bridge's Pillars toggle instead of placing objects (below). Trees store their bare species; the renderer draws a placed or imported tree's `-snow` form while it stands on a snow surface (snow terrain or a snow theme), unless its inspector's Snow toggle is off, which saves `"bare": true` on the object. Seaport container yards and cranes on woods (`fluff:80`, `81`) become the woods' container yard look (a design, below); a crane tip (`fluff:82`) that a converted crane's boom reaches places nothing, any other becomes a Crane boom segment. An animal herd (`fluff:13`) imports as its individual animals in one group, from the herd image the tileset chose for that hex. The editor reports `Imported <file>: N objects in M groups`. First the conversion gives a legacy `.board` (never a `.board2`) the values its aliases drew as: pavement 4 becomes pavement 1 with its exits derived again, pavement 5 and up pavement 3, mud 2 mud 1; the shipped boards store these values.

The conversion places objects for FLUFF below 2000 (server rubble is terrain-owned), `road_fluff:3` roadside trees and, on a board not converted yet, the road-with-trees art of `road:2` (on a converted board `road:2` is the native Alley finish): one predicate, `BoardSceneryLayouts.imported` through `TilesetScenery.Layer.taken`; since batch 10 it takes every other art token as a design or as nothing (Legacy conversion, batch 10, below). It keeps the taken tokens on the board in memory, so a game, the lobby and a map preview of an old `.board` still draw the old sprites in 2D; a `.board2` and the editor's document never hold them (above). Rule terrain is kept, with one exception, a car park's lane road and the automatic neighbouring roads that meet it (below): roads, woods, water and buildings stay. It also gives every bridge without a type its type (Bridge types, below) and then marks the board native, which means converted: converting a converted board or a `.board2` only types bridges that still lack a type, so no board is decoded twice. The 3D board never decodes a token: every 3D view captures each hex without its taken tokens (`BoardTiles`, the one capture, through `BoardSceneryLayouts.withoutTakenTokens`), so a game and a preview draw exactly what the editor and the saved `.board2` hold. A board that reaches a 3D view unconverted (a load site that skipped the conversion) logs `Unconverted legacy scenery ... a load site skipped conversion; it is not drawn` once and draws nothing for its taken tokens; there is no fallback decode. A Fluff value that names convertible art and reaches a hex through a session command (`TERRAIN`) or a pasted foreign hex text (`MegaMek Hex` clipboard text) is converted when its stroke commits, in the same undo step (above).

**Sheets, seams and old saves.** A game converts each sheet on its own, before it is flipped and combined, so a turned sheet keeps its art and its car-park lanes turn with it. One pass then runs on the combined board (`BoardSceneryLayouts.joinSheets`, called by `BoardUtilities.combine` for every game board assembly and after an old save's boards are converted): a bridge span crossing a seam whose hexes store different types becomes built (each hex keeps its own Pillars state; the decode is an OR over the span), and the two halves of a 7-hex emblem set cut by a seam, which each placed the full emblem on the set's centre, become one emblem. Halves on a flipped sheet do not coincide and stay. An old save is converted on its combined board, so a span or an emblem crossing a seam there can differ from a per-sheet conversion; saves made since batch 9 hold the converted board. An old save that combined a `.board2` sheet with `.board` sheets (possible on this development branch before batch 9) is native as a whole, so its legacy sheets are not converted: every 3D view draws them without the art the conversion takes, with no objects in its place and no warning, while their 2D board still draws the sprites. A `.board2` written before batch 9 that holds a Fluff value naming convertible art shows none of it in 3D either (the editor drops the value when it opens the file).

**Legacy conversion (batch 10).** The conversion takes every legacy art token, so a `.board2` holds none: FLUFF and GROUND_FLUFF below 2000, ROAD_FLUFF, WATER_FLUFF and BLDG_FLUFF. One function states what stands for each (`BoardSceneryLayouts.takenTokens`):
- **Objects** (as before, `Layer.taken`): batch 10 adds data only. Runway markings become `decal/runway/*`, the one-hex landing pads `decal/landing-pads/*`, the heli pads the `heli-pad` decal with one or six `scenery/roofs/landing-light` GLBs in one group, letters and digits `decal/lettering/*`, courts `decal/sport/*`, rails route markers (Legacy rails below). A letter is one white decal; a black one stores its paint colour (a decal may hold one colour, slot 0, which the decal material multiplies; Edit shows it as one Paint colour). A DropShip pad or emblem set with pieces missing on the board paints exactly its present pieces: each gets the set's decal on the set centre, clipped to its own hex, one group per set, no issue; a set cut by the board edge keeps its full emblem and its issue. A decal row of a layout is folded back to back only when its decal has car slots (car parks), so a heli pad lies where its row places it.
- **A design** that draws exactly the token's art: the blueprint variant whose `selectors` equal the token (`BoardEditorBlueprint.reproducing`), written by the conversion unless the owner already has a design, which wins. Transitions become `ground/blend/<family>` at strength exits/6, kerb bends and the blank `road_fluff` on roads `road/rounded`, `road_fluff:2` `road/horizontal`, orchards `woods/orchard`, container yards and cranes the container yard looks with their rotation, rough art `rough/obstacles` or the new `rough/felled-trees`, building art (`bldg_fluff:1`–`54`, `100`) the 55 new `building/legacy-art-N` designs, and art beside which the building's structure model was chosen that model's asset design (barn, farm, church, ...). Quay art becomes its `ground/quay-N` design, for the 2D board only: the 3D views derive the fitted quay wall. Designs are syntactic, so a turned sheet keeps the authored transition strength (the old exits flip scrambled it).
- **Nothing:** the tileset's transparent wildcard (`saxarba/misc/blank.png`, decided per hex from the matched layers) and `bldg_fluff:0`.

Server values (FLUFF 2001–2005, GROUND_FLUFF 2000) are game state and never taken. Elevator plates and the cleared-rubble gravel stay rows of their rule terrain: each becomes a decal of its hex (`BoardFeatures`, never stored or picked, following the elevator's level), drawn once in the Tactical View too. A design token a gamemaster types in a game gets its design on the edit, through its own helper (`BoardSceneryLayouts.designTypedTokens`, called by `HexEditHandler` for a set terrain, a painted hex and a cleared hex): retyping the token changes the design and removing it drops the design it stood for, unless another was chosen; `withoutTakenTokens` only drops tokens, and no `.board2` is fixed up: a `.board2` that still holds a design token (a draft saved before batch 10) loses that art, as the editor drops the token on open, and a game of it draws the token's sprite in 2D but neither the token nor a design in 3D. The gamemaster's building edit keeps a building's art level as token and design together (`BoardSceneryLayouts.buildingArt`, `setBuildingArt`); clearing or replacing the building drops both. The renderer draws designed layers in tileset order, the kerb and orchard rules read the owner's design, and the Tactical View's base tile selects with the designs. On the 755 shipped boards with tokens (scratch count on this build, 2026-10-10; `LegacySceneryCorpusTest` pins it): 12,044 rail markers (137 on bridge decks, 105 of them the rail a rail bridge carries across its span; a rail crossing under a bridge lies beneath it), 4 level crossings (a decal and 4 signals each), 4,525 runway decals, 978 heli pads with 4,443 landing lights, 588 landing-pad decals (85 complete DropShip sets, and 503 one-hex pads and pieces of the 40 incomplete sets), 395 letters (68 black) and 142 courts; designs on 9,759 building-art hexes, 108 building-model hexes, 66 quay hexes, 6,705 transitions, 19,749 rounded and 1,760 horizontal road hexes, 4,291 orchards, 4,224 container yard looks (3,819 Container rows, 193 Quay crane yard, 212 mirrored) and 2,281 rough hexes (1,314 obstacles, 967 felled trees); every remaining token (3,215 blank, 191 `bldg_fluff:0`) dropped. No converted board reports an issue. Every conversion with its legacy sprite beside the 3D result: `docs/design/board-editor-v2/handoff/b10-report.md` (captures by `GpuLegacyArtReportSmokeTest`).

**Container yards (batch 12).** A container yard is a look of the woods cover (owner `vegetation`, Vegetation > Looks and Industry > Seaport): five designs `woods/container-yard/*` (Container rows, Scattered containers, Quay crane yard, Quay crane yard mirrored, Gantry yard), each naming one composition per cover level (foliage, light, heavy, ultra), turned by the hex's `rotation`. Every 3D view draws the composition of the hex's cover level (`BoardSceneryLayouts.skin`) as objects its woods own (`BoardFeatures.decorations`): instanced, shadowed and faded as placed objects, never stored, picked, edited or listed in Layers or Issues. A quay crane's boom reaches over the next hex (its end 108 px out) and turns with the look; a click under it picks the hex under it. A sheet loaded turned (a rotated board in the lobby, `BoardUtilities.flip`) turns each look half round with its hexes and objects; a flip along one axis (scenario boards) mirrors it: the two crane looks are each other's mirror image (`mirror`), the other looks stand for their own (rows read alike mirrored). The woods draw no trees there (`BoardTreeDistribution.noTrees`, which the Classic tile art follows), and the Tactical View hides the yard with the placed objects. Woods cleared to rough draw no yard, woods burnt down a level the lower level's composition; the look stays on the hex. A look without art at a level draws the Rows composition there (data). The 2D board of a `.board2` draws the legacy sprite of the nearest legacy rotation (a half turn reads as the same rows, a crane's exact heading first; Scattered and Gantry yard draw the Rows sprites); the tileset has yard sprites only for `woods:1`, so a heavy or ultra yard shows its woods there and a cleared one nothing. A game of a loaded `.board` keeps the hex's own token where it is one of that rotation's sprites (its own colours); a turned sheet's crane draws the sprite of its turned heading. Where a fitted concrete wall reaches a yard's rows, its hex keeps its outline, the rule of placed objects. `.board2` files written before batch 12 keep their legacy yard objects and "No trees"; re-importing the legacy `.board` gives the look. The 78 legacy seaport models stay loadable for them, off the palette. In the editor a look's card paints its cover with the look (Scattered: foliage); Brush and Edit offer "Rotation (clockwise)" (0-330, step 30) on a yard look; a stroke paints one look and one rotation; changing to another yard look keeps the rotation. Industry > Seaport also holds the props: Container (one, two or three high), Quay crane, Crane boom segment (snaps end to end to a quay crane's boom end and to other segments), Yard gantry (normal or tall), Straddle carrier, Reach stacker and Yard truck.

**What changed for 2D players.** The converted board is the one game board, so its rule changes reach 2D players too: the car-park lanes are real roads (426 lane hexes on 23 shipped boards, 18 neighbouring roads written out; below), drawn by the 2D tileset as roads. The 2D board of an old `.board` keeps its sprites, since the tokens stay in memory; a `.board2` has none. The 2D "3D-only content" warning is gone from games, the lobby and SBF, and the in-game Save board writes `.board2`, as every game board is converted.

What the conversion changes against the old render of a `.board` (until batch 9 a game drew an old `.board` through a second, render-time decode of its tokens; that path is gone):

- Car parks (`fluff:5`, the cars_1–8, 2b and 3b sprites): the old render paved a road lane through cars_1–8 from the parking sprite's FLUFF token and left the cars where the sprite drew them. The conversion places standard car-park decals instead (`decal/car-park/straight-4`, `-8`, `-12`, `parallel-3`, `-6`, `diagonal-3`, `-6`, `-9`): one per side of the lane that has cars, beside the lane's road: its road-side edge 7.3 px from the lane's centre line, where the road's asphalt has half faded (`BoardRoad.Kind` half width 7.5 less half of `GpuRoads`' 0.45 px feather), so the decal hides the road's gray verge and leaves its carriageway and centre dashes clear; a two-sided park is the same decal twice, the second turned 180°, one on each side of the road, the smallest standard of the cars' layout with room for the fuller side's cars. Each is only its row of bays: white-lined bays on plain asphalt, open on the road side, with its back line and end dividers on the image's edges, no aisle and no road markings. Where no road is drawn, import folds the same rows back to back (`BoardSceneryLayouts.Plate`): each row turned 180° and mirrored onto the line through the hex centre along its lane, the two closed outlines touching there and the bays opening outward; the mirror keeps every car on its side, in its order along the lane and in its paint, and straight cars still park nose-in. That is every car park without a lane (2b/3b), on a roof, deck, industrial top, fuel tank, ice or water, on a hazardous liquid or molten magma, or with an authored road level the renderer does not draw (5 and 6): about 121 of the 1,870 shipped car parks by a text scan, the others beside their road. The decals are rows of the car-park layout, so they belong to its group, and each car row's `"seat": [n, slot]` parks that car in slot `slot` (`decals.json`) of the layout's `n`-th decal row: the decal row's position, turn and scale applied to the slot, and the slot's heading added to the decal's turn; the car keeps its asset, paint and scale. Cars therefore move from their legacy spots (beside the road up to 22.0 px, mean 3.7–12.5 px per sprite; back to back up to 23.0 px, mean 8.7–13.4 px), keeping their order along the lane. Rows are placed at import: editing the road afterwards does not move them, and folded rows carry the decal's mirror flag, which Edit shows like any mirror. A `.board2` imported before the rows moved beside the road (2026-10-09) keeps its old row positions and seats, so its cars sit about 2 px off the new bays until it is imported again; no shipped `.board2` uses car-park decals. On plain ground (no roof, bridge deck, industrial top, fuel tank, ice or water: the support rule that seats the decals and cars), import gives a car park without a road of its own its lane as a real road, `road:1` with the lane's two exits specified: cars_1/4 `road:1:18` (NE-SW), cars_2/5/7 `road:1:36` (SE-NW), cars_3/6/8 `road:1:09` (N-S), the exits the old render paved. It runs edge to edge between the two rows of bays, fully visible, and it joins every road and car-park lane that points along it; elsewhere it ends square at the hex edge, as the legacy lane did. **This changes the rules of the map in every game, 2D players included**: the lane is a road for movement, elevation change, hidden deployment (none on it), digging in and fortifying (no longer allowed on it), Urban Guerrilla, black ice and landing (no clear-ground or mud landing modifier, and a landing DropShip leaves no crater). The hidden-deployment, digging-in, Urban Guerrilla, black-ice and landing effects already apply on pavement, so they change only on the 105 lane hexes without pavement (on 9 boards, 56 of them on the two Solaris Arena Maze boards); on pavement, movement barely changes. A car park on a roof, deck, industrial top, fuel tank, ice or water gets no road, because its sprite was decoration there, nor does one on a hazardous liquid or molten magma, where the renderer draws no road. An authored road on a car-park hex is kept with its exits, and the rows stand beside it (a junction's side arm still passes under one row, 45 car parks by a text scan). cars_2b and 3b, which have no lane in the legacy art, get car-park decals back to back but no road. A road meeting the car park off its lane still ends at the hex edge. A neighbouring road with automatic exits off the lane keeps the exits it loaded with, written out as specified (18 hexes on the two 64x68 airfields), so it grows no arm toward the car park; it gains only an exit toward another car park whose lane points at it, whichever car park import meets first. An automatic road on the lane gains its exit toward the car park and joins it (none on the shipped maps). Captures: `decals/spaceport-imported-cars*.png` and `decals/car-park-roads-imported-*.png`. The palette offers the eight standard decals as "Car park, straight 12" and so on (Ground details).
- Emblems (`fluff:50`–`62`, the Saxarba ground symbols: Red Cross and twelve faction emblems): the old render painted their tileset images. The conversion turns each into a decal of the emblem's one full image (`decal/emblems/<name>`, 144 × 144 model px at scale 1; `decals.json` maps every legacy image id to it). A piece of a 7-hex set (codes 7–13: 10 the centre, 7 N, 9 NE, 12 SE, 13 S, 11 SW, 8 NW) names its set's centre hex, so all seven become ONE emblem at scale 1 on the centre hex, unclipped, spanning the six neighbours, on the centre hex's support. Since batch 10 a set with pieces missing on the board paints exactly its present pieces (the emblem on the set centre, clipped to each piece's hex, one group, no issue); a piece beyond the board edge counts as present, so a set cut by the edge still gets its full emblem at the inferred centre, and the editor lists an issue on it (`Emblem set with 5 of 7 pieces: the full emblem is placed`) for as long as that emblem stays on that hex; a centre beyond the board edge is owned by the first piece's hex, at the centre's offset. A one-hex variant (codes 1–6) becomes the full emblem clipped to its hex at its fitted scale (small 0.204–0.326, large 0.346–0.503 per emblem) and turn (1/4 upright, 2/5 −30°, 3/6 +30°). A FLUFF code without a piece draws nothing and, since batch 10, is dropped. Every decoded emblem token is taken: kept in a game's memory for the 2D board, never drawn in 3D and never written to `.board2`. A set cut by a sheet seam becomes one emblem once the sheets are combined (above). The emblem paints on the hex's roof, deck or ground like the legacy art (`decals/spaceport-imported-roof.png`). The shipped boards hold 23 sets and 226 one-hex variants; none is incomplete.
- Garden lakes: the shipped template (`boards/Templates/PoolsGardens.board`, the only board that uses them) and the tileset select them as plain `fluff:94:N`, without `water:0`, so no full-hex water is drawn there. No tileset entry with WATER in its terrains resolves to a 3D model (724 such entries in the renderer's tileset), so the renderer has no special case for decorative water: a hand-made `water:0` under lake art is drawn as game water.
- Heights are sampled at each object's own anchor instead of on one plane at the hex centre, so objects on a slope or near a support edge follow what lies under them. Ice and fuel tanks are supports, as in the old render: ice ledges stand on the ice, beacons on the tank. An anchor outside its chosen deck, roof, industrial top or fuel tank takes that support's height at its hex centre, as the legacy composition's shared plane did, and only falls back to the ground when the hex has no such support: a roof pool's tree beyond its building's curved roof stays at roof height.
- Pillar art on a bridge hex (`fluff:4:06`–`11`, the pillars1–6 art: a `layouts.json` layout whose rows are all `scenery/parks/pillar`) is the bridge's Pillars toggle, not objects: one predicate (`BoardSceneryLayouts.bridgePillars`) decides for the conversion, which turns the toggle on (`"appearance":{"bridge":{"variant":"bridge/pillars"}}`, `HexAppearance.PILLARS`), places no objects and takes the token. On any other hex the art stays six plain Pillar objects on its support, with no stretch and no special rule; the palette Pillar is an ordinary object. The 3D views draw one concrete pier under each joint between two hexes of a toggled deck, never at a hex centre (docs/gpu-natural-bridges.md, Piers); a one-hex bridge rests on its landings and a deck at ground level (Sirius V) has no room, so neither shows one, though both keep the toggle. The Pillars toggle sits in a bridge's Edit panel (select the Bridge row in Layers, or press the deck or a pier in the side view): it shows the selected hex's state, and a click sets the whole connected bridge (its `BridgeSpan`, the hexes a deck-height drag moves) to the other state as one undo step (`BoardEditorSession.Action.PILLARS`); off writes `bridge/built`, so the bridge stays built. The toggle is a built type, so only a built bridge shows it, and switching the bridge to Natural or removing it clears it; Use as brush, copy and paste carry it. Bridge pillars that a development build stored as stretched Pillar objects in a `.board2` are not migrated; re-import the legacy board to get piers.
- Maglev on an industrial hex rides an implicit guideway at the industrial top. On water it rides a guideway at the water surface, including a zero-elevation deck above a submerged bed. Its train and station pieces follow that deck; unsupported parked cars stay omitted. Building or fuel-tank roofs cannot carry an additional bridge, so those maglev routes and their riders are omitted with a conversion issue.
- Seaport crane tips (`CraneTip-1-01`–`06`) that no converted crane's boom reaches are one Crane boom segment (`scenery/seaport/yard/crane-boom`) at the hex centre along the tip's line (rotation 0, −60, −120 for tips 1/4, 2/5, 3/6), on the hex's own support; 44 of the 105 shipped tips.
- Pool trees sit 1.6 px lower on the deck than in the old render, because their rows are at z = 0 (tree meshes are shared species assets).
- Concrete fit beside placed objects: the fit itself is `common/board/ConcreteFit` (plain Java over one cell per hex), which `BoardConcrete` caches per scene for terrain, water, artwork and picking and the legacy conversion reads too. A placed object keeps its hex's concrete outline (pins it) only where the fit moves a wall or bank into it: an edge toward another level or beside a liquid whose corners moved sweeps at least 4 px² of the object's footprint inside its own hex (`ConcreteFit.reaches`; the footprint is its model's bounds placed by scale, stretch, turn and anchor, a decal's stamp or a maglev route's guideway, `BoardObstacles.outline`). An edge moved away from the object, a touch, or a moved edge between two dry hexes of one level does not pin. Structures (buildings, industrial, bridges, fuel tanks) keep their hex. A pinned hex can move other edges, so the fit repeats until no further object is reached; `GpuTerrain`'s refit check reads the same features (`BoardConcrete.fitFeature`) and the hexes' Edges (`BoardConcrete.edges`): a Fitted hex is never pinned by its objects, a Hex hex keeps its outline. The legacy conversion (an old `.board` only; a `.board2` is drawn as authored) moves each minor object the unpinned fit would cut the shortest way clear of the walls and banks of its hex, half a pixel clear (`BoardSceneryLayouts.clearOfConcreteWalls`, footprints from `BoardModelBounds`: the GLB's `-lod0` bounds); the members of a group in the hex move as one, by one offset, so the art keeps its layout. Objects that follow the hex sides (route markers and the pieces that ride them, decals, roof parts, seaport pieces) stay and pin, as does an object whose model file is missing or unreadable on the converting machine, one that would move more than 42 px, and every member of a group with such a member. Over the 187 shipped boards whose fit moves something, 324 hexes pin under the old rule (any overlap with the swept band), 223 under this test and 176 after the conversion's moves (171 by edge-tied objects; 5 by minor ones: the pillar groups of Defiance Industries Mechbay 0410, 0610, 0810 and Labryinth v4 2018, which cannot step clear within 42 px, and Op2M3 2737's crawler crane beside a ledge-pinned hex). The conversion moves 308 objects on 44 hexes of 19 boards (196 picnic tables, 50 trees, 19 construction debris and excavations, 14 plazas and gardens, 11 crawler cranes, 10 vehicles, 6 park pillars, 2 pools; per hex median 6.0 px, at most 23.3 px). It runs before a sheet is turned and the fit is not symmetric under the turn: turned, the 58 boards with pins have 16 hexes pinned by minor objects (on 7 boards).
- The Tactical View draws imported objects in 3D instead of a sprite, and does not draw cosmetic trees.
- 2D views draw no objects. A game's or a preview's 2D board of an old `.board` keeps its sprites (the tokens stay in memory); a `.board2` holds no legacy art token, so its 2D view (the editor's 2D Preview included) shows rule terrain, lane roads included, and the art of its designs through the 2D tileset's design hook (above). Lobby thumbnails and the advanced-search table read the file unconverted.
- Tree species and headings are fixed at import; their winter form follows the hex's snow surface when drawn, so a later snow or theme edit swaps it.

**Bridge types.** The appearance owner `bridge` stores built, natural, truss or implicit type, with the corresponding Pillars variants. Ground, deck and their ways remain separate rules layers. `BridgeSpan` finds connected bridge hexes with reciprocal exits and decks within one level. Inspector span actions and deck-height drags use that connected span; painting a bridge card affects only its visited hexes. Legacy conversion repairs accepted one-sided bridge exits before saving their explicit masks. Native `.board2` exits and types are read as authored.

- **Decode** (`BridgeSpan.decode`, the one rule): a type stored on any hex of the span decides, built winning over natural. Otherwise the span is built when any of its hexes has any of these:
  - a road: ROAD on the hex at any level, or a deck exit landing on a road hex at any level, with or without a road exit back;
  - rail or maglev art on the hex or at a deck end (FLUFF 10 or 9), before conversion replaces it with rail terrain;
  - pillar art;
  - PAVEMENT terrain on the hex or at a deck end (snow-covered pavement included: the terrain counts, not the drawn surface);
  - a BUILDING on the hex or on any of its six neighbours.

  Otherwise the span is natural.
- **Who applies it:** only legacy conversion. It decodes the loaded board before adding car-park lanes, while pillar and rail art are still available, and stores the result. Generated bridges already receive explicit type and deck ways. A `.board2` is read as saved and receives no bridge-type or route-marker migration.
- **The 3D board never decodes:** it reads the stored type and each hex's own deck-road and deck-rail terrain. An untyped transient or scenario-added bridge draws as a clean built deck. A road below or beside it never repaints an authored span; changing a neighbouring building does not change its type.
- **Corpus** (2,546 spans on the 488 shipped boards with bridges, by first reason): road 2,193 spans (6,568 hexes), pillar art 4 (4), pavement 192 (420), rail 16 (63), a building 41 (1,292, among them 20 of BaelCity's 24 boardwalk networks), natural 100 (274). Since BaelCity's four one-hex pieces got their missing exits (2026-10-10) the shipped boards hold 2,542 spans, 2,446 built and 96 natural (270 hexes): each piece joined its built boardwalk. `GpuBridgeSmokeTest.corpusExamplesDrawTheTypeTheConversionStores` draws one converted span per reason in its stored type (`bridges/corpus-<reason>-imported.png`).
- **Built by engineers:** a bridge they build or repair in a game (`BridgeConstruction`) is stored built (a rebuilt section that had piers keeps them). The type is appearance; the game's Save board writes `.board2` anyway, since every game board is converted.
- **Editor:**
  - The Bridge, Natural bridge and Truss bridge cards draw explicit clean decks using the shared Height controls. Painting a card changes only the visited deck hexes; it does not retype connected neighbours. The inspector's Built/Natural, Standard/Truss and Pillars actions deliberately apply to the whole connected span.
  - **+ Add Bridge** creates an explicit built deck on the selected hex. Implicit decks are created and removed by the ways they carry; they do not convert neighbouring explicit decks.
- **Look:**
  - A clean built deck has its own concrete surface. Deck road and deck rail terrain decorate only the hexes that carry them; a road on the ground or at a landing does not repaint an authored span. Legacy conversion settles inferred deck ways before editing.
  - A bare landing gets a dirt-and-gravel apron, but not on a bank drawn as pavement (snow-covered pavement is drawn as snow and keeps the apron).
  - A natural span is a rock arch and never has piers.
- **Supports:** flat and sloped built decks share generated bridge facets as the `bridge` support for the hover ring, click-to-place, decals and the side view.
- **Truss design (b10-f1):** a built span is drawn as the standard deck or as a riveted steel pony truss (`BoardBridgeTruss`, docs/gpu-natural-bridges.md, Truss). The design is a built type, `bridge/truss` or `bridge/truss-pillars` with piers (`HexAppearance.TRUSS`, `TRUSS_PILLARS`; `HexAppearance.truss`, `pillars` and `bridgeBuilt` read it). A truss stores its colour like a placed object, one `#rrggbb` per colour slot (the truss has one, Body, Oxide red by default; nothing is stored for the default colour): `"appearance":{"bridge":{"variant":"bridge/truss","colours":["#2e5233"]}}`. Only a truss may store colours (`HexAppearance` refuses them on any other variant, `validateOwner` on any other owner). One design and one colour hold for a span: `BridgeSpan.truss` (a truss when any hex stores one; its colours those of the first hex by column, then row, that stores any), read alike by the 3D board and the editor. The legacy decode never makes a truss, so converted boards keep their look; rules and the 2D views ignore it.
  - Edit panel: under Built / Natural, a built bridge shows **Standard / Truss** (`Action.BRIDGE_DESIGN`, the whole span in one undo step, each hex keeping its piers and a truss its span's colour), Pillars, and for a truss a **Truss colour** row: the object inspector's swatches and `#rrggbb` field (one helper, `GpuBoardEditor.colourRows`), `Action.BRIDGE_COLOUR`, the whole span in one undo step. Pillars and Built keep the design and colour; Natural drops both. Painting or adding a bridge does not silently change its neighbours' stored design or colour.
  - Palette: a third card, "Truss bridge" (`bridge/truss`); a stroke paints only its visited deck hexes as truss, while the Built card paints only its visited deck hexes as standard. Use as brush, copy and paste carry design and colour.

**Ground cover around stationary content** is decided when a hex is built, never per frame. Units and meeples stand in the grass and never bend or clear it.
- **One obstacle rule,** `BoardObstacles`, for grass blades, bank turf, reeds and crops, the dressing baked into the terrain and captured scatter. It covers:
  - structures and placed objects;
  - pier footings;
  - each bridge deck: its passage from the hex centre to each exit edge, `BoardBridge.PASSAGE_HALF_WIDTH` each side, from the slab's underside to the deck.

  Cover tall enough to reach a deck's underside does not grow there, so a deck at or near the ground has no grass through it. A raised deck leaves the ground beneath it as it is.
- **Decals:** grass, turf, reeds and crops avoid them (`BoardDecals.Opacity`). The dressing baked into the solid terrain (BoardScatter pebbles, tufts and bushes, BoardRelief field stones and shrubs) does not. Testing decals there would make every decal edit, a paint-only update today, rebuild the solid terrain. That stays for the pending one-scatter-path consolidation.
- Roof furniture no longer raises the nominal height that CPU consumers read (firing-arc clearance in `BoardFiringGeometry`, camera framing in `BoardCamera.fitTop`, cosmetic footprints in `BoardObstacles`): every legacy key converts into objects on the roof (rows at z = 0), while a single-mesh key used to carry its roof level as the feature's elevation. The building itself still gives each consumer its roof level, the arcs keep one level above it, and every roof mesh is at most 18.3 model px tall (the glass dome; one level at the default level height). Folding the roof level into the rows' elevation would lift the drawn rows by the roof height, because the render adds a row's elevation to the solid support it finds; this is documented rather than given a second, CPU-only height.

**Legacy maglev** (`fluff:9`) converts into `rail:2` on the ground or `bridge_rail:2` on its existing or new implicit deck. Temporary route objects exist only inside the converter; saved boards and runtime routes use the terrain. A new suspended guideway is `bridge:4` with CF 650 and the original absolute height. It uses the maglev beam as its support and picking surface, without a concrete slab beneath it. Pillars belong to the bridge appearance and use the slim maglev pier. An existing deck retains its type, CF, exits and ground content.

The accepted legacy census is 1,903 ground routes, 257 new implicit decks (72 at elevation zero over water, 200 with Pillars), 23 routes on existing decks, and 28 routes over buildings omitted with an issue. This changes gameplay intentionally: elevated and water-surface guideways are walkable, attackable bridge structures; their collapse removes their carried rail and riders. The ground beneath remains independent. Two elevated routes at different heights in one hex cannot be represented.

Station platforms and train vehicles remain ordinary grouped objects, reanchored to the resulting ground or deck. Their heading, colour and placement within the hex are retained. Plain legacy track tokens go away; station/train composite tokens remain in memory for Legacy 2D parity and are drawn above the new rail sprite. The `.board2` writer drops these legacy tokens. The native example board stores its guideway and riders in the new form. A `.board2` is read as authored, without route-marker migration.

**Legacy rails** (`fluff:10`) convert to `rail:1` or `bridge_rail:1`, with explicit exits and optional junction layout in the rail appearance. They leave no stored route object. Side-less rail art connects to neighbouring rail art; isolated art creates no rail. Legacy rail-only bridge spans carry rail along their deck, with a clean concrete surface. Roads beneath remain ground roads. Road/rail crossings keep their crossing signals and use the shared corridor renderer for track, paving and markings. On dry ground, stranded hairpin sides that lie entirely in a road are dropped during legacy conversion; valid gentle pieces remain. Rail and maglev never join each other. Native files are not repaired during loading.

Every 3D view (game, lobby, map preview and the editor, the Tactical View included) draws placed objects one way since batch 13 (b13-scope item 6, replacing b9-decisions D9's two strategies): each object is an instance of its model's shared mesh, faded and cut away with its building, and its parts draw with the instancing path of shared building modules: one draw per model part, not one per placed part, and a drag preview only changes the instance data. A mirrored placement is instanced too: the instance data carries the mirror and mirror images draw in a batch of their own with the front face flipped (`GpuInstancedMesh.mirrored`). Parts whose pose the instance data cannot hold (a tilt, a shear, or a different X and Y stretch) and materials without an instanced shader draw one by one. Plain placed trees stand in the instanced tree stand with its detail levels. The Tactical View hides placed plants as it hides every other plant, so they are neither drawn nor picked there; every other placed object stays in 3D, visible, pickable and selectable. Every view keeps each object's id (picking data for the editor and GM tools); game picking still reports hexes, never objects. Picking, selection, drill-down, drag previews and undo read the placed instances, never the draw caches. Maglev routes keep their own route handling in every view.

**Small objects at a distance (Object LoD).** Every 3D view, editor and game alike, skips decorative placed objects smaller than a quarter hex (the diagonal of the placed object's world box; terrain-owned layout rows are packed with the terrain and never hide) while a hex is narrower than 12 pixels on screen: they hide below a 10.8 px hex and return above a 13.2 px hex (`TreeLod.SMALL_OBJECTS`, the tree levels' ±10 %), so no object wider than about 3 pixels is ever hidden. The size class is set once, when a hex is built (`GpuTerrain.Prop.small`); the zoom decision is one per camera (`updateDetail`); one predicate (`GpuTerrain.drawn`) serves the colour, shadow, depth, wireframe and transparent passes, picking and box selection, and the game's combat scars on objects (a scar on a hidden object hides with it and returns with it, `GpuTerrain.scarShown`). Never hidden: objects of a quarter hex or more, buildings, bridges, fuel tanks, industrial structures, rough, rubble, geysers, trees and plants (they have their own detail levels), maglev routes, decals, units and markers. Perspective and first-person views never hide anything, like grass. The selected objects (a whole selected group too) and the objects hovered in Layers or the side view always draw and can always be picked; they cast no shadow while their zoom hides the others. A hidden object cannot be hovered or clicked: the click passes through to the hex below, and a box at such a zoom selects the hexes, not the objects nobody sees; Layers, the inspector and the side view still list every object. A zoom crossing alone does not redraw the shadow map (like a tree level change): the next redraw, which the zoom usually brings, applies the rule. Limitations: a composite layout whose parts differ in size loses its small parts first (the sport-3 wading pool before its main pool), and what is hidden depends on the window's pixels (a 4K overview of Valencia hides nothing).

**Object mesh levels (b10-f1).** A placed object whose model file has simpler mesh levels (`<name>-lod1`, `-lod2` groups) draws the level the buildings' rule chooses (`GpuTerrain.Prop.detail`, one method for buildings and objects): the larger side of its placed bounds on screen against `TreeLod.PROPS` (80 and 24 px, ±10 %), so LOD0, LOD1 and LOD2 at most (a plant's impostor cards, LOD3, are the tree stand's only). Every view draws the instanced shared mesh of the chosen level (`GpuAssets.objectLevels`: `GpuAssets.slotted` per level, colours per draw). A placed object's level change gathers the chunk's object parts again (a building's still rebuilds the chunk's prop caches, `recacheProps`); shadows draw the chosen level from the next shadow redraw (the change alone does not redraw the map). Measured before batch 13 (b10-fverify, RTX 4070, Valencia with 40 trains and 20 orchard trees, 164 objects with levels): steady frames did not change, but each frame in which objects changed level cost about 131 ms in the game and 63 ms in the editor, against 7-8 ms for the same zoom steps without levels, because the recached chunk's packed props rebuilt its `GpuPropBatch` page (b10-ffix measured 100-165 ms in the game on the Iris Xe). Batch 13 draws the game's levelled objects from the instanced meshes as well, which was the open point; the cost of a level change has not been measured again since. Picking, placement and supports stay on LOD0 (`Prop.pickingModel`), and the small-object rule above still hides small objects. A file's level count is read from its JSON (`RigidGlb.levels`); a model with one level gets no level list and costs nothing per frame. Placed models with levels today: the 13 rail and 9 maglev vehicles (a detailed LOD0, the earlier mesh as LOD1; couplers, platforms, buffer stops, crossing signals and routes have one level) and the plants the tree stand cannot hold (tilted, mirrored or unevenly stretched trees, corals and fungi). A level may hold a material another lacks (the six orchard trees' fruit is on LOD0 and LOD1 only): it takes the placement's culling, fade and cutaway from the placement's other materials (`Prop.level`, b10-ffix). The editor's side view is a close-up: it draws a building's or object's near level whatever level the board's zoom chose (`Prop.near`).

Lobby discovery, board filtering/indexing, server selection, board combination and reflection accept `.board2`. Combining repeated sheets gives duplicate instances fresh IDs. Reflecting a board preserves legitimate high-valued legacy artwork selectors and transforms object positions, yaw and mirror state.

## Blueprint and adding content

The canonical catalog is `mm-data/data/board-editor/blueprint.json`. Gradle stages it to `megamek/data/board-editor/blueprint.json`. Edit the canonical file. The catalog is read on first use; restart the application after changing it. It maps all 61 terrain properties to 20 contextual groups. Engine-derived properties and unresolved legacy selectors are preserved rather than offered as arbitrary new paint.

**Text.** The editor's own text (toolbar, tool hints, Brush, Assets, Layers, Edit, Settings, Help, the issues list, the side view, the right-click menu and the session's messages such as "Opened …" or "Save failed: …") comes from `messages.properties` through `BoardEditor.*` keys; the toolbar's Open/Save/Save as, the brush's Theme, Resize, Flood, level change and a few more reuse the old editor's keys and their German, Spanish and Russian translations. `GpuEditorTextKeysTest` fails on a hard-coded label in the editor's view classes and on a key the code names that does not exist. The catalog's labels (components, fields, choices, presets, designs, assets and families) are data: they show as `blueprint.json` writes them, in English, and are not duplicated as message keys. The palette's category and section names are keys (`BoardEditor.palette.<category>` and `BoardEditor.palette.<category>.<section>`); a new category or section needs its key, which the same test checks. The session's refusals of malformed commands (for example "Unknown brush setting") stay developer English.

The catalog contains the existing building manifest designs, individual prop models, stamps, the maglev and rail routes and rolling stock, decals (the 13 emblems, the 8 standard car parks, the rubble path, 26 runway markings, 13 landing pads, 36 letters and digits, 4 courts and the level crossing; emblem pieces and one-hex variants are decode-only, and elevator plates and the cleared-rubble gravel belong to their rule terrain), ground blends, road finishes and the legacy designs (`rough/felled-trees` and the 55 `building/legacy-art-N`, family Legacy building art). It contains no invented water styles: the installed water-fluff rules only supply a blank fallback.

Components specify `receiver` (defaults to the component ID) for the Layers hierarchy, and `category`, of which only `Structures` is read (the height join of structures). Rubble is a Feature; painting it does not change the hex theme. The industry component declares `receiver: "industrial"` to match its existing support identifier. Numeric fields can specify `min`, `max` and `step` for their sliders; these are UI metadata and do not replace game-rule validation. `height: true` exposes a field in Hex section. Discrete `choices` provide readable selectors instead of unexplained numeric codes; road choices also declare their linked `material`.

Components also declare `presets`: complete, validated terrain recipes with stable IDs and readable labels. `replaceExisting: false` makes a recipe additive within its component. An asset entry may name another `model` and its `colours` (see Colour slots): the three ponds are the freeform, sport-2 and sport-4 pools in their pond colours. A palette entry is one real object a user places, or a stamp: no palette ID is a `layouts.json` key, rotated and baked duplicates are gone, and terrain-owned scenery (rubble, geysers, fortifications) is painted through its terrain, not offered as a prop. `BoardSceneryDecodeDataTest` checks these rules and the palette objects per section.

`categories` lists the Assets start page in order: an `id`, an `icon` (one hex in the `.board2` hex form) and its `sections`; the Theme category has `themes` (the special themes Dirt and Rock) instead. Names are message keys `BoardEditor.palette.<category>[.<section>]`. A preset, variant or asset is on the palette when it names a `section` (`category/section`, or a list: a decal with a purpose is in its purpose section and under Decals, one entry shown twice); without one it has no card and stays loadable. Entries sharing a `family` are one card: assets a picker, variants a gallery. Cards follow data order (presets, variants, assets). A preset's `settings` are optional fields the Brush offers; painting a preset gives a hex that lacks it the preset's terrain outside its component (Hazardous liquid, `water:1;hazardous_liquid:1`, adds its water to a dry hex and keeps a lake's depth), except that the Lava preset makes the hex's magma liquid and removes a hazardous liquid, and Water removes magma, crust too (the two liquids replace each other); `hexes` makes it a multi-hex blueprint (the DropShip: by direction N to NW the terrain of each neighbour). A choice field with `brush: true` is a Brush row. A variant's `pieces` picks its model by the building's weight and exits. The palette has 9 categories, 53 sections, 252 cards (277 places, as a decal with a purpose shows twice) and 4 galleries. For example:

```json
"presets": [
  {"id":"woods-1","label":"Woods","terrain":"woods:1;foliage_elev:2","section":"vegetation/gameplay"},
  {"id":"jungle-1","label":"Jungle","terrain":"jungle:1;foliage_elev:2","section":"vegetation/gameplay"}
]
```

A vegetation variant with `skin` draws scenery instead of trees (the container yard looks): `layouts` names a `layouts.json` composition for each cover, `foliage`, `light`, `heavy` and `ultra`; `legacy` lists, by clockwise rotation, the legacy tokens the look stands for (the conversion and the 2D board; each token stands for one design); `sprites` names the skin whose sprites a look without legacy tokens draws in 2D; `mirror` names the skin that is its mirror image across its east-west axis, which names it back (a board flipped along one axis shows it); `cover` (default `light`) is the cover its card shows and paints (an excerpt):

The library uses compact preview cards. Road surfaces have rendered cards in the inspector. Hex theme and visual design share a two-column row, labelled with their current values. Themes use one gallery, shared by the per-hex and global selectors: each sample is a triangle of three mutually touching hexes, with a raised cliff behind clear ground and vegetation at level zero. All eight installed terrain themes fit together at 1280×800, without search or paging. The tileset's synthetic Transparent entry is excluded; the empty legacy theme is displayed as Grass, without a duplicate Default choice. Simply opening a map does not rewrite its stored themes. Selecting a global theme previews the choice, and Apply changes the document as one undoable edit. Visual cards have no repeated-name tooltips, and the gallery has no explanatory footer. Numeric captions retain their gesture instructions.

Material and theme galleries share UIKit's `UiChoiceGrid`. It measures the content and available viewport, chooses a suitable number of columns, and grows cards by up to 50% when the complete grid still fits. The extra height enlarges the preview while keeping captions at their normal text size. A short viewport adds columns when space permits; overflow scrolls vertically. `UiKit.fitChoices` measures a dialog's existing header, footer and padding before fitting its grid. Resizing preserves the card actors, their actions, focus and loaded previews. The library uses `UiCardGrid`; Layers are a `UiTree`, whose surface stacks use `UiList` for drag reordering. The editor uses smaller side panels and inline toolbar utilities, with the same ten-stage-unit outer margin and toolbar clearance as the preview/gameplay HUDs.

`UiKit.fitSearch` collapses an optional search row, including its vertical padding, when all choices are visible. The editor measures the unfiltered layout without search before checking overflow, so a search bar cannot create its own need to exist. A larger catalog or constrained viewport restores it; an active query always stays visible and clearable.

Right-click starts with Select, Sculpt, Paint and Erase and their keys, followed by Line of Sight, Undo/Redo, Group/Ungroup and Board settings. The right-click does not change the selection. Top view, Isometric view and Fit board are three square icon buttons at the top right. Side view in the right-click menu collapses or expands the side view; no key is bound to it (Z, X, C and V are tools). Right drag still pans. LOS and Alt-click use the shared ruler model and native LOS panel; completing a measurement does not paint, even with Paint selected. Wheel input over the board clears stale panel focus; Ctrl+wheel commits a pending number before changing elevation.

The selected hex carries a small N and arrow projected from its north edge. The arrow follows camera rotation and perspective while its lettering stays upright and readable. It shares the selection ring's height and passes pointer input through to the board. Cliff, road and bridge connections use UIKit's `UiHexSides`, following MegaMekLab's building-door control: click a hex side or its compass label to toggle it; selected sides are mint. The widget reports directions to the existing editor commands, which retain validation, automatic connections and undo.

Hovering a side or direction label in the Cliff edges control highlights the matching side of the inspected hex's board outline in gold. Leaving the control clears the highlight. Applied cliff-top modifiers add a second mint stroke inside the inspected hex's selection outline, derived from the editor snapshot so edits and undo/redo stay in sync. Both use the same board geometry and depth handling as the selection outline.

Continuous numeric/section edits apply to the EDT-owned document as before, but the existing 33 ms capture timer publishes intermediate scene snapshots. Release commits and captures immediately. Empty elevation captures no longer bump the inspector revision. Active editor terrain rebuilds get a twelve-millisecond render-thread slice, versus two milliseconds for ordinary camera refinement.

Native model placements borrow asset meshes independently of the static terrain cache. The editor presents position, rotation, scale, mirror and height changes as soon as a snapshot arrives; the main cameras, hex section, model picking and shadows share that pose. Placement uses the installed ground/deck/roof and the existing placement calculation. Pending rebuilds retain their original inputs, then replace the temporary pose and surrounding terrain/vegetation together. New/deleted models, changed assets, decals and terrain edits still wait for geometry installation; this is not a general instant terrain rebuild.

Rotation uses one row of X, Y and Z inputs in both the inspector and prop/decal brush. X tilts about east-west, Y tilts about north-south, and Z turns about the board's vertical axis. The right-handed Euler transform applies X, then Y, then Z. Format 2 retains `rotation` for Z and adds optional `rotationX` and `rotationY`; zero tilt is omitted, so existing objects keep their pose. Drawn meshes, picking, shadows and vegetation clearance use the same transform. Surface decals remain projected stamps: X/Y tilt foreshortens their footprint instead of lifting them off the receiving surface. An edge-on stamp has no footprint. Existing horizontal magnetic connectors do not snap tilted instances.

Stretch scales an object along its own width, length and height (X, Y, Z) on top of its uniform scale: the local scale is `scale` times `stretch` per axis, applied in object space before the rotations. `.board2` stores it as an optional `"stretch": [x, y, z]` (positive factors, omitted when 1, 1, 1). The session edits it as the object values `stretchX`, `stretchY` and `stretchZ`; a live drag is one undo step, like any value. Edit shows them as the Stretch × row under Scale: W, L and H for a prop, W and L for a decal; a maglev route has none. Duplicates, copies, pastes, moves, flips (the mirror flag stays separate, so each local axis keeps its factor), sheet combination and group edits keep it; a group scale stays uniform and multiplies `scale` only. Drawn meshes, picking, bounds, the section view, shadows and vegetation clearance use the one transform; paint stretches its stamp. Magnetic connectors place ends with the stretch and join only objects of equal scale and stretch. Legacy decode rows in `layouts.json` take the same optional `"stretch"`, read once by `BoardSceneryLayouts` for the conversion.

**Colour slots.** A model may mark up to four colour slots: each vertex carries its slot in the GLB attribute `_COLOUR_SLOT` (0 for none), and the file's extras `mmColourSlots` name each slot, its default sRGB colour and its preset colours. An object's `colours` replace them in slot order: `.board2` stores an optional `"colours": ["#rrggbb", null, ...]` (null keeps a slot's own colour; omitted when every slot keeps it). Each channel keeps its ratio to the slot's default in linear light, so the shaded parts of a slot stay shaded (`RigidGlb.recolour`). Legacy decode rows take the same optional `"colours"`, which the conversion gives its objects. The families that differed only in colour are one mesh each: the car (paint; 19 meshes before), hen (plumage; 6), rooster (plumage, wings; 3), horse (coat, mane and tail, muzzle; standing 3, resting 2), cow (patches; 2), pig (skin, spots; 3, canonical the pink spotted pig) and bison (coat; 2), and the pools whose ponds were their copies (wall, coping, deck, water: freeform, sport-2 and sport-4 carry the pond rows; 6 meshes before). Edit shows a Colours section for a prop with slots: per slot a row of preset swatches (the family's former colours; the mint frame marks the current one) and its colour as `#rrggbb` to type any other; each choice is the object value `colour0` … `colour3`, one undo step, and the model's own colour stores nothing. Duplicates, copies, pastes, moves, flips, sheet combination and group edits keep the colours; a decal has none. Until batch 13, outside the editor (game, lobby, map preview) the renderer built one recoloured copy of a model per set of colours (`GpuAssets.model(name, colours)`), merged by the packed prop pages; that copy remains only for layout rows and the editor preview's ghosts. Every view now draws one shared mesh per recolourable model (`GpuAssets.slotted`, `RigidGlb.colourSlotMesh`): each vertex also carries its shade relative to its slot's default colour and its slot, each placement passes its four slot colours (`RigidGlb.packed`) in its instance data, or as a uniform for the parts drawn one by one and in the side view, and the vertex shader applies `RigidGlb.recolour`'s rule in exact sRGB (`model-colour-slots.glsl`), before any lighting. It reads a packed colour by truncation (`uint(c)`): the value arrives as an exact integer float, and rounding it (`+ .5`) would move every odd value from 0x800000 up one step (white drew black, magenta red). So in every view every colouring of a model is one instanced draw per part, a custom colour adds no mesh, and a rebuild that reuses a hex or a drag preview keeps the placement's colours (they travel with the instance's `userData`). Measured with `GpuSceneryColourSmokeTest`'s overview (every car park, suburb, pool, pond and herd, and 19 trees on snow): with one copy per colour set in every view the draws were legacy 30, imported game view 88, editor 165 (the `GpuLegacyImportSmokeTest` close-up: preview 55, editor 99); on 2026-10-09, with the editor's shared meshes and the later car-park decals, the overview frames drew legacy 31, imported game view 77 and editor 110, and the editor's opaque pass drew 109 both with every object in its model's own colours and with the fixture's colours. The editor's close-ups of the 66 fixture hexes, including a mirrored magenta car (drawn one by one, the uniform path) and an upright white one (instanced), match the game view's CPU-recoloured copies: 0 pixels differ by more than 2/255, except 2 pixels on one hex. From batch 9 to batch 13 the two draw strategies shared everything but the recolour step and the chunk caches, held together by KEEP IN SYNC comments and a pixel-parity test (of 70 captures 61 to 62 were identical to the bit, the others within 1/255 but one pixel). Since batch 13 there is one strategy; the remaining KEEP IN SYNC comments describe placed objects against the packed buildings and scenery (`drawn`/the packed caches' Tactical View rule, `addDecorations`/the packed caches) and the GPU recolour against the CPU copies (`RigidGlb.recolour`/`model-colour-slots.glsl`, compared per vertex by `RigidGlbTest`). One fade rule serves every prop: a placed object fades with a hovered or occupied structure, faded props are submitted in a stable order (libGDX's blended sort ties for a distant camera), and a fade that ends restores each prop's own culling (a mirrored placement drawn one by one keeps both faces; an instanced one keeps its model's culling, as its batch flips the front face; `GpuTerrain.culling`).

**Snow trees.** For 19 species (the six orchard trees, pine, pine-broad, pine-slender, pine-layered, tree-broad, birch, willow-broad, tree-layered, birch-spreading, birch-young, tree-slender, tree and birch-tall) the winter form is a material variant of the bare GLB: its materials' extras `mmVariants.snow` name the snow canopy material and textures, a factor on the crown's vertex colours (the snow cards drop the species' pigment) and the winter impostor's texture and lighting colours. `RigidGlb.source` reads `<species>-snow` from `<species>.glb` with that variant when there is no `<species>-snow.glb`. pine-tall, tree-dead, willow, tree-forked and the snow foliage keep their own `-snow` GLB.

UIKit's `UiNumber.angle()` uses `UiAngleDial`. Clicking the caption opens it; holding and dragging the caption starts adjustment immediately, and release commits and closes it. A straight drag turns the angle, from the caption or on the dial, with the cursor hidden and held: right and up add, left and down subtract, half a degree per unit, continuously across the wrap boundary. A click on the dial points it there. Typing commits on blur and wraps equivalent angles into -180 to 180 degrees. The dial follows MekBay's dials in UIKit's colours: a ticked scale (every 10 degrees, brighter every 30, zero in mint) around a recessed well, the turn from zero in mint along the well's rim to the needle's grip, and the value in a dark hub. Its discs and its round-ended stroke are `UiTheme` nine-patches (`dial-*`) rasterised at the dial's sizes, so the dial owns no GPU resources. The dial reads as a compass: zero points up and a positive angle turns clockwise. The board stores right-handed rotations, positive counter-clockwise seen from the axis's positive end (Z from above), so the editor's rotation inputs (X, Y, Z and the group's Turn) show the negated value and send the negation of what they show: a drag to the right turns the number up, the needle clockwise and the object clockwise. Saved `.board2` values keep their sign, so existing boards look the same; a value read in the file is the negation of the one the editor shows.

Salvage terrain uses separate board models, `salvage/arm` and `salvage/leg`, independent of the unit equipment model. Their editable Blender source is `mm-data/tools/board-models/salvage/limbs.blend`; the arm has 288 triangles and the bent leg has 480. In source space, +Y faces forward and the limb runs along Z. The renderer lays each limb on its side, centers its bounds and grounds its lowest vertex. Hex-seeded random positions and headings replace the repeated radial layout. Interleaved stable slots keep the remaining salvage in place when a limb is collected.

Authored deployment-zone terrain is marked in the editor with its zone label and the shared deployment perimeter effect. Adjacent hexes in the same zone omit their internal boundary. Isometric view shows the perimeter wall; top view retains the flat outline. These editor markers leave the ground untinted. Perimeter geometry is derived when the terrain snapshot changes, not on pointer movement.

A decal's footprint is its `size` from `decals.json` times its scale and stretch, centred on its position. Each decal image is its own mipmapped texture (`GpuAssets.decorationPaint`: trilinear, 8× anisotropic where supported, clamped at its edges), so no other image's texels bleed in at any mip level. The images are straight alpha; their transparent texels carry the nearest ink's colour (the rubble path included), and `GpuAssets.paintTexture` builds the mip levels itself, averaging colours by alpha as premultiplied filtering would (glGenerateMipmap would weigh transparent texels' colours equally: simulated over grey, that tinted mip levels 1–3 by up to 47 of 255 at the emblems' multi-coloured edges, and by 37 at the rubble path's before its bleed). Bilinear filtering within a level still mixes neighbouring texels without alpha weights. Decals still share draws: a chunk draws its paint in painter order, one draw per run of the same image (a decal joins the latest draw of its image unless a decal of another image drawn after that one shares a hex with it), and these numbered draws (`GpuDecalOrder.layer`) merge with the same draws of nearby chunks in `GpuTerrainPages` in the isometric view. Measured in `GpuDecalReviewSmokeTest`: the 39 emblem decals of its board add 16 draw calls to its overview frame (3 without them; 45 when every decal was its own draw per chunk); the 22 decal textures with full mip chains take 2,480,300 bytes (RGBA8; 3,172,180 before the car parks became rows of bays only), loaded on first use. Cross-hex decals use one logical owner and a recipient index shared by chunks and cameras. A changed owner recomputes its old and new footprints; unchanged footprint lists are reused. Moving, scaling, replacing or deleting paint invalidates the union of affected recipients, without the solid-terrain neighbour rebuild radius. Paint-only changes replace a separate authored-paint mesh layer and re-plant, on the terrain worker, the ground cover of the hexes whose paint changed, preserving installed terrain, props and texture atlases. Projection uses the installed detail level; camera refinement can change it independently. Receiving geometry is reused when cached and reconstructed on the worker when absent. No decal copies are written into neighbouring hex records. Undo uses the same path. Picking any painted recipient returns the original owner and object ID. Paint order is a material attribute used by the renderer's sorter, rather than a tiny height offset that can disappear in depth precision.

**No ground cover through paint.** Grass blades, bank turf, reeds and crops grow by one minus the opacity of the paint on the hex's ground (`BoardDecals.Opacity`, used by `BoardPlants` and so by every 3D view: game, editor, previews and imports). The opacity is each placed decal's image alpha at its drawn transform (position, turn, tilt, scale, stretch, mirror and `clipToHex`, the same `paintUv` the paint uses), read once per image on any thread, so a round emblem leaves no square bald patch, a car park's opaque asphalt clears its whole row and the soft rubble path thins the cover; and the legacy paint overlay the full 3D render draws on legacy boards (legacy emblems, rubble paths, cleared-rubble gravel, metal deposits, transitions), mapped as the ground's top vertices map it. Each paint counts with its largest alpha within one model px, the margin cover keeps from a road's shoulder; cover vanishes where the paint is more than about 45 % opaque. Only paint on the ground counts: roofs, decks, industrial tops, fuel tanks and ice grow no cover. A root's place and growth chance are drawn before any rejection, so the roots outside the paint keep their places and ranks, and removing a decal brings back exactly the previous roots. Planting builds the opacity once per painted hex on the worker; unpainted hexes pay one null check per root, and nothing runs per frame. Limitations: the ground dressing baked into the solid terrain (captured pebbles, grass tufts and bushes of `BoardScatter`, and the field stones and shrubs of `BoardRelief.field`) does not follow the rule yet; it moves under it when that dressing joins the worker planting (the pending "one scatter path" consolidation), so hand-placed and large decals on open ground can still show a pebble or shrub on the paint (the shipped maps' imported car parks are unaffected: their hex's road excludes the captured scatter, and their objects the field dressing). Relatedly, a paint-only edit that gives a featureless hex its first decal, or removes its last, leaves that hex's field dressing as it was until its terrain is next rebuilt (a fresh build has none under a decal). A ground decal under a bridge deck thins the cover under the deck where it is painted, and the legacy overlay of a bridge hex, drawn on the deck, also thins the cover below it (very rare). A `clipToHex` decal's restriction to its anchor's support level inside its hex is not modelled for cover (ground receivers are one welded level). Blades lean up to about 4 px, so oblique close-ups can still show blade tips over a decal's outer line, as over a road shoulder.

Terrain previews use private sample boards and the existing artwork resolver, terrain renderer and atmosphere composite. They decode artwork off-thread and build progressively, with a bounded image cache. The preview renderer borrows the board renderer's `GpuAssets` (`new GpuTerrain(lender)`), so a first sample no longer decodes the sculpt texture array again on the render thread; `GpuAssets.retain` keeps every model either renderer still draws, and a new board renderer (an asset reload) replaces the preview renderer. Measured in `GpuEditorSelectionControlsSmokeTest` with temporary probes (this machine): the frame of the first terrain sample took 958 ms with private assets, most of it the sculpt array's decode. With shared assets, four runs on 2026-10-08 (other GPU work running on the machine) show the first sample still stalling two frames: 132–184 ms for the preview renderer's own construction (110–163 ms: its own shaders, procedural textures and oceans), then 145–179 ms for its first build, nearly all of it decoding the vegetation hex's three tree species (89, 56 and 23 ms in one run), which the board had not drawn yet and which the shared assets then keep. Every later sample's frames took at most 36 ms. Not yet done: sharing the board renderer's shaders and textures with the preview renderer, and decoding models off the render thread. Model cards load only for the grid's created rows. Search, category changes and resizing recalculate navigation and visibility. Stamps show static thumbnails. Missing preview art leaves the reference selectable and displays a short unavailable indicator.

A component may specify an optional `preview`, for example `"preview":{"terrain":"road:1:9","level":0}`. Its terrain defaults to the component's existing `defaults`, and its level defaults to zero. This describes only the sample card, never the terrain that a user paints. The cliff sample declares level 2; road and bridge samples declare visible connections. New visual styles and themes use the same content lookup as the board.

Add a prop GLB under `data/models/board/` and an asset entry:

```json
{"id":"scenery/custom/solar-panels","label":"Solar panels","kind":"prop","section":"industry/construction"}
```

Its ID is the logical model path without `.glb`; without a `section` it has no card. An optional `thumbnail` is a path relative to `data/`. A stamp is an ordinary prop entry with a `layout` naming a `models/board/scenery/layouts.json` key, for example `{"id":"stamp/tree-cluster-1","label":"Tree cluster 1","kind":"prop","layout":"scenery/saxarba/SMV_Fluff/FluffSystem-07-Garden-01-Tree-1-01","thumbnail":"…","section":"vegetation/blueprints","family":"Tree cluster"}`; `{exits}` in the layout is replaced by the painted hex's road exits as two digits. Stamps use static thumbnails. New building cards are variants with `owner: "building"`, an `asset` using the existing building adapter and an optional thumbnail. No new fluff number is needed:

```json
{"id":"building/custom/workshop","label":"Workshop","owner":"building","section":"buildings/looks","asset":"buildings/custom/workshop","thumbnail":"editor-previews/workshop.png"}
```

For paint, add the image as `models/board/decals/<folder>/<name>.png`: its id `decal/<folder>/<name>` finds it by that path convention (`BoardDecalArt`), without the catalog, in the renderer and in the editor's missing-art check. Give it a `size` (model px at scale 1; a hex is 84 × 72, the default) in `decals/decals.json`, and register `kind: "decal"` with a label and a `section` in the catalog for the palette (a list when it has a purpose: its purpose section and its `decals/…` section); its card shows the image found by the same path convention. For a new road material, add a Godot 4 Standard material (`<stem>.tres` with its albedo, normal, heightmap and ORM maps; see [board materials](gpu-board-materials.md)) under `models/board/textures/roads/`, catalogue it as loose in `textures/materials.json`, register a variant with `owner: "road"` and its `material` stem, and assign it to the applicable road field choice. Missing complete material sets retain the renderer's existing fallback. An asset's optional `snap` defines its compatible `set`, radius, angle tolerance and connector arrays `[x,y,z,heading]`; XY use hex dimensions, Z uses levels and heading uses degrees. Adding asset cards, labels or materials needs data changes only. New gameplay semantics or receiver types require code; future released format changes must remain explicitly versioned so older readers refuse data they cannot preserve. This unreleased work remains version 2.
